# 013 — a single Binance WS `exception` restarts all eight clients, unguarded

Bug spec (SKILL.md Part 0). Scope: `src/price/binance.ts` — `binanceErrorCb`'s
response to an exception, and nothing else.

Spun off from spec 012, which fixed only the *log payload* of this handler and
left its recovery explicitly out of scope (012 §5). This spec covers the
recovery's **rate**, not its **radius** — see §3.

## §1 Definition

### §1.1 Expected

**§1.1a — repeated exceptions collapse into one restart cycle.** The handler
returned by `binanceErrorCb` is registered on **all eight** clients
(`getBinanceClient`, four ticker + four candle) and `stopBinance()` recreates
all eight whichever one faulted. A run of exceptions must therefore start at
most **one** teardown + re-subscribe cycle, and the guard must **coalesce
(drop)** the rest — not queue them. The `IdMutex` used elsewhere in this file
serialises, which would still run N full restarts back to back.

Note which run actually matters. A *same-tick* burst from all eight clients is
already largely self-limiting: `stopBinance()` runs synchronously and its
`getBinanceClient(…, current)` calls `current.removeAllListeners()` on the old
clients, so the siblings' exceptions land on the replacement no-op handler. The
run that is **not** self-limiting — and the one production logs — is a
*sequence* on the live client, one per second (§1.2b, §1.3).

This is the shape the two sibling venues already have: `bybit.ts:238-305`
(`bybitRestarting`, bug #121, `12293be`) and, in a weaker form, `okx.ts:411-425`
(restarts only on a `503`). Binance is the only connector with no guard at all.

**§1.1b — the guard is held until the cycle's re-dial has settled.** A restart
does not finish when `init()` resolves; see §1.2b.

**§1.1c — benign SDK replies are logged, not answered with a restart.** The
sibling connectors classify `handler not found`, `format error` and `already
subscribed` as informational and log them at `info`. Restarting on a
self-clearing reply is what started the bybit storm.

### §1.2 Actual

**§1.2a — every exception starts its own full cycle** (`src/price/binance.ts`
:238-249 at HEAD):

```ts
private binanceErrorCb(e: ExchangeEnum) {
  return (data: any) => {
    logger.error(`${e.toUpperCase()} error: … ${describeWsException(data)}`)
    this.stopBinance()   // recreates ALL EIGHT clients
    this.init()          // re-subscribes every ticker + candle stream
  }
}
```

No re-entrancy flag, no message classification.

**§1.2b — even a bybit-shaped guard would release immediately here.** bybit's
guard is held for the lifetime of its cycle's promise, which is ~15s because
`initBybitWS()` contains three `await sleep(5000)`. Binance's `init()` has no
such body:

- ticker role → `initBinanceWS()`, three synchronous `subscribe*` SDK calls;
- candle role → `reconnectBinanceCandleStream()`, which calls
  `connectBinanceCandleStreams` — and that method's first act is to **arm a 5s
  debounce timer and return** (:440-447). The dial it schedules runs ~5s later
  and then issues one 200-stream chunk per second (`await sleep(1000)`, :476).

So `init()` resolves in the same tick, and a guard scoped to it would be
released *before* the re-dial it just scheduled has even started — leaving the
exceptions raised by that dial free to tear down the sockets it created. The
guard has to outlive `init()`.

### §1.3 Evidence

**Production, `Gainium <-> Binance candle stream connector`** (read-only `logs`
helper, 2026-09-18T06:0xZ). Fixed-string search for `BINANCE error: main`
(which excludes the `BINANCEUS` lines of spec 011) returned the capped tail of
2000 lines; every one of them is one full eight-client teardown:

```
2026-09-17T20  319
2026-09-17T21  191
2026-09-18T00   77
2026-09-18T01   66
2026-09-18T02  101
2026-09-18T03  490
2026-09-18T04  754   (in 34 min → ~1330/h, ~0.37/s)
```

This whole window is **one uninterrupted process life**: the connector's boot
line (`Price connector families … streaming: …`) last appears at
`2026-09-17T19:14:34.697Z` and never again, so every count above was produced by
the same binary — the one with the handler quoted in §1.2a. (Spec 011 §4's
reading that this process restarted at `04:29` onto `v2.13.17` is not supported
by its own log: no boot line exists after `19:14:34`.) The international volume
stops at `2026-09-18T04:34:06Z` with no restart, i.e. the underlying fault
self-cleared; the handler's behaviour did not change.

Inter-arrival gaps cluster hard at **1.0s** (880 of 1999 gaps at exactly 1.0s,
1233 in the 0.8–1.3s band) — the `await sleep(1000)` between chunk dials in
`connectBinanceCandleStreams`. The exceptions are therefore **not** a same-tick
burst: they arrive one per second, spaced by the connector's own re-dial loop,
which is precisely the pattern a guard released at `init()` would not catch
(§1.2b).

**Local probe of the real SDK against the real venue** (2026-09-18, this host,
outbound only — the connector's exact client settings, `connectToWsUrl` on
`WS_KEY_MAP.main`):

- the international combined-stream URL **works from here** and raised **zero**
  exceptions in 25s, so the fault behind the production volume is not
  reproducible off the production host and is not this spec's subject;
- dialling the same `wsKey` three times 1s apart (the multi-chunk shape) raised
  **no exception** — spec 011 §4's "reused wsKey" hypothesis is refuted for the
  healthy case;
- a 404 URL produced `{"wsKey":"main", kMessage:"Unexpected server response:
  404", kType:"error", kTarget:…}` followed by `reconnecting` — i.e. **the SDK
  already recovers the faulting socket on its own** (`parseWsError` →
  `executeReconnectableClose`, `reconnectTimeout` 3500ms). Our family-wide
  teardown is a second, coarser recovery layered on top of it.

**Deterministic reproduction, two levels.**

*Unit* — `test/binanceRestartStorm.test.ts`, the real
`binanceErrorCb`/`runBinanceRestart` driven off the prototype against a fake
`this` that counts cycles (the idiom of `test/bybitRestartStorm.test.ts`). This
isolates the handler's own coalescing, with no sibling-silencing side effect:

```
pre-fix  8 exceptions, same tick     → 8 stopBinance()+init() cycles, 8 concurrent
pre-fix  6 exceptions, 1 per tick    → 6 cycles
pre-fix  3 benign replies            → 3 cycles
post-fix each of the three           → 1, 1 and 0 cycles
```

*Integration* — a real `BinanceConnector` (`PRICEROLE=candle`) with its eight
real SDK clients, exceptions emitted on the clients the constructor actually
registered the handler on, `stopBinance()` counted by wrapping the real method.
This is the number to trust, because it includes the self-silencing of §1.1a:

```
            8 same-tick, then 4 spaced 1s apart on the live client, then
            one more after the settle window
pre-fix     1 → 5 → 6 teardowns   (8 clients recreated each time)
post-fix    1 → 1 → 2 teardowns   (8 clients recreated each time)
```

So the same-tick burst is *not* where the damage is; the 1-per-second sequence
is, and it is exactly what the production gap histogram shows.

### §1.4 User-visible consequence

Each cycle calls `closeAll()` on, and reconstructs, all eight clients — including
`binanceUS`, `binanceUsdm` and `binanceCoinm`, which are on separate endpoints
and were not faulting. At ~0.4–1.3 cycles/s no Binance socket survives long
enough to complete a handshake, so bots on every Binance market lose their
price/candle feed and fall back to the 2.5-minute REST poll, while BYBIT /
BITGET / OKX open normally in the same process.

## §2 Assumption (hypothesis)

**§2.1** The handler has no coalescing flag, so the *rate* of teardowns is set
by the rate of exceptions rather than by the cost of a recovery. A
`binanceRestarting` boolean that drops concurrent restarts, held until the
re-dial `init()` scheduled has had time to settle, reduces any burst — same-tick
or 1s-spaced — to one cycle. The test in §1.3 must fail on HEAD *because* the
flag is absent, and pass with it.

**Origin: latent.** The unguarded `this.stopBinance(); this.init()` pair dates
to `38b5d4f` (2025-06-26, `chore(release): 1.0.2`) — nearly fifteen months. What
is new is the *exception volume* reaching it, not the code.

Note for anyone re-blaming the diff: `git blame` reports **`868243c`
(2026-09-18)** for those two lines, which looks recent. `868243c` is the
*revert* of spec 011 revision 1 — the scoped per-client recovery that was
refuted in production — so it **restored** the 2025 shape rather than
introducing it. `git log -S "this.stopBinance()" -- src/price/binance.ts`
returns exactly three commits: `38b5d4f` (introduced), `7c1090b` (011 rev 1,
removed), `868243c` (revert, restored).

## §3 Out of scope

- **The recovery's radius.** Spec 011 revision 1 shipped a scoped, per-client
  recovery here on the claim that the binanceUS 404 was tearing down the
  international feeds; that claim was refuted in production and rolled back
  (011 §4). This spec does not re-narrow the radius: a fatal exception still
  restarts the whole family, exactly as today. Only the rate changes.
- **Why the international `main` connection fails on the production host at
  all.** Not reproducible from here (§1.3) and not fixed by this
  spec. The guard stops that failure from destroying the other seven clients;
  it does not stop the failure.
- **`closeBinanceCandleStream()` closing nothing.** The probe showed candle
  sockets opened via `connectToWsUrl` are never registered in the SDK's
  `wsStore`, so `closeAll(false)` does not close them and candle messages keep
  arriving after it. That is a separate defect with its own reproduction; it is
  filed separately, not fixed here.
