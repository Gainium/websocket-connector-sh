# 009 — Kraken futures `fills`: order a multi-fill batch chronologically, and derive FILLED from the cumulative total

Bug spec (SKILL.md Part 0). Kraken **futures** only (`ExchangeEnum.krakenUsdm`,
feed `fills`). Kraken **spot** (`executions`) and the futures `open_orders`
feed are different payload families and are out of scope — `open_orders` was
fixed separately (`src/utils/krakenOpenOrders.ts`, 2026-08-22).

## §1 Definition

### §1.1 Expected

`prepareKrakenOrderMsg`'s `fills` branch turns each entry of a Kraken futures
`fills` message into an `ExecutionReport`. `ExecutionReport.totalTradeQuantity`
is the contract's **cumulative** executed quantity — `app-sh` assigns it
straight to `order.executedQty` — and `orderStatus: 'FILLED'` is the contract's
**terminal** signal: `app-sh` books the fill and stops expecting more.

For an order that executes in N chunks, therefore:

- **§1.1a** the emitted reports must carry a **non-decreasing** cumulative
  quantity, ending at the order's full size;
- **§1.1b** **exactly one** report may be `FILLED`, it must be the **last** one
  emitted, and its `totalTradeQuantity` must equal the order's full size. Every
  earlier report is `PARTIALLY_FILLED`;
- **§1.1c** every report's `quantity` (the order's original size) must equal
  the size actually placed, on every report — not just the terminal one. It is
  what makes `executedQty < origQty` mean what the engine thinks it means.

### §1.2 Actual

A Kraken futures `fills` message may carry **several fills in one payload**
(`msg.fills` is an array), and Kraken delivers that batch **newest-first**.
`src/userStream.ts:4700` maps it in array order and `:4737` takes the status
from **that one fill's** `remaining_order_qty === 0`.

The chunk that brought the order to zero remaining is therefore mapped
**first**, so the relay emits `FILLED` carrying the *smallest* cumulative
total, then the true totals behind it as `PARTIALLY_FILLED`.

Observed live, 2026-09-14, `krakenUsdm` BTC-USD, order
`D-BO-lDG9nW4K2gWCFBHnoyMggTj5oIHmgc` — a LIMIT BUY of **0.0955** taker-filled
in 4 chunks (0.0139 + 0.0404 + 0.0316 + 0.0096), all stamped 15:00:02.492Z.
Relayed as:

| # | emitted status | `totalTradeQuantity` | `quantity` |
|---|---|---|---|
| 1 | **FILLED** | 0.0139 | 0.0139 |
| 2 | PARTIALLY_FILLED | 0.0235 | 0.0374 |
| 3 | PARTIALLY_FILLED | 0.0551 | 0.0786 |
| 4 | PARTIALLY_FILLED | 0.0955 | 0.1506 |

Three violations of §1.1: the terminal report is first and 6.9× short
(§1.1b), and `quantity` — computed as `totals.qty + remaining`, which is only
the order size when the running total is the *chronological* cumulative —
drifts to 0.1506 for an order of 0.0955 (§1.1c).

### §1.3 Downstream consequence (why this strands coins)

`app-sh` treats the first `FILLED` as final and logs the later, correct totals
as `already processed`. On that first report the buy-remainder path
(`app-sh core/src/bot/main.ts` ~L5707) saw `executedQty 0.0139 < origQty
0.0955` and sent a market BUY for the 0.0816 "shortfall" that the venue had
**already filled** — doubling the entry. The take-profit was then sized from
0.0139, and the deal closed on it. Venue net: +0.0955 +0.0816 −0.0139 =
**0.1632 BTC held with no deal, no TP and no SL**.

## §2 Evidence

- **Prod log** `Gainium-DCA-bot-out__2026-09-14_15-55-31.log.gz`:
  `15:00:03.599 Processing msg BTC-USD D-BO-lDG9n…, FILLED, 78460, base: 0.0139`
  then `base: 0.0235 / 0.0551 / 0.0955 -> already processed` at
  15:00:04.212–.213. The 611 ms gap before the last three is `app-sh`
  processing report #1 synchronously (it placed `GA-BR-UClNdxoOSSAMC0g3CkScmbCNB9V5R`
  at 15:00:04.210) — i.e. all four reports were relayed from **one** WS
  message, then dequeued one at a time.
- **Kraken REST `/fills`** for that order: 4 chunks, 0.0139 + 0.0404 + 0.0316 +
  0.0096 = 0.0955, all at 15:00:02.492Z → the order was fully filled at the
  venue before any of this.
- **Local reproduction** (`core/test/krakenFillCumulative.test.ts`, test
  *"a multi-fill batch delivered newest-first…"*): replaying the batch
  newest-first through the real `prepareKrakenOrderMsg` reproduces the §1.2
  table exactly, including the 0.0235 / 0.0551 / 0.0955 cumulative sequence in
  the prod log. The array order is reconstructed *from* that sequence: emitted
  cumulative #k = 0.0955 − `remaining_order_qty` of fill #k, which is
  self-consistent only for a strictly reverse-chronological batch.

## §3 Assumption (hypothesis, not fact)

The root cause is that the branch has **no notion of fill order**:

- **§3.1** it never sorts `msg.fills`, so the running accumulator added by
  a777b8d (2026-08-07, bug #332) sums the batch in delivery order and its
  running value is not the chronological cumulative;
- **§3.2** `orderStatus` is taken from a **single fill's**
  `remaining_order_qty`, which is a statement about that fill's position in the
  *chronological* sequence — the one thing the branch does not know.

a777b8d fixed the cumulative-total half of this (each report now carries a
running total rather than the per-fill `qty`) but left both §3.1 and §3.2
untouched, and its tests only ever emit **one fill per message**, so the batch
path was never exercised. `src/utils/krakenOpenOrders.ts` fixed the sibling
`open_orders` feed, which carries `filled` as a venue-supplied cumulative and
so never had this problem.

## §4 Solution shape

- **§4.1** Map the batch in chronological order: sort a copy of `msg.fills`
  ascending by `time`, then by `seq` as tiebreak (the 4 chunks above share a
  millisecond, so `time` alone does not order them). Non-mutating — the caller's
  message is not ours to reorder.
- **§4.2** Track the order's size per order id, monotonically
  (`size = max(size, cumulative + remaining)`), and derive
  `FILLED` from **`cumulative >= size`**, not from one fill's
  `remaining_order_qty`. Emit `size` as `quantity` (§1.1c).
- **§4.3** Compare with a small absolute tolerance: the cumulative is a float
  sum (0.0139 + 0.0404 + 0.0316 + 0.0096 does not land exactly on 0.0955), and
  an exact `>=` would drop the terminal `FILLED` — turning this bug into a
  permanently-open deal, which is worse than what it fixes.

## §5 Non-goals

- **§5.1** The `app-sh` half. Making an already-`FILLED` order accept a larger
  cumulative `executedQty` (monotonic update), and gating the `krakenUsdm`
  buy-remainder on a venue fills/position check, are defence-in-depth in a
  **different repo** (`main-app-sh`) and are not in this spec.
- **§5.2** Sweeping/reconciling the 495 historical `krakenUsdm` GA-BR orders,
  or the already-stranded balances on the reporting account. Operational, not a
  code fix.
- **§5.3** Cross-**message** reordering (a batch split across two WS messages).
  §4.2 makes the relay converge on the right total, but the first report can
  still be wrong; only §5.1's monotonic update closes that. Called out so it is
  not mistaken for covered.
