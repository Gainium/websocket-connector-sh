# 003 — Forward the venue's fee on every exchange, not only Binance

Part 1 of a three-repo initiative (`app-sh` specs `006`/`007` are the other
two) to make `deal.commission`/PnL reflect the fee the venue actually
charged, for every venue, in real time. This spec is this repo's slice only:
get the fee onto the wire. What `app-sh` does with it is out of scope here.

## §1 Current behaviour

### §1.1 Binance — already forwarded

`src/utils/binance.js` reads Binance's raw `m.n`/`m.N` (spot) and
`m.o.n`/`m.o.N` (futures) — per-trade commission + the asset it was charged
in — and adds them as `commission`/`commissionAsset`/`tradeId` extra
properties on the object handed to `userStreamEvent()` (`:134-136`,
`:232-235`). These are not declared on the `ExecutionReport` TS interface
(`src/userStream.ts:259-277`) but the interface does not filter the
object — the cast at `src/userStream.ts:1922,1924-1927` is `as
UserDataStreamEvent`, decorative — so they reach `redis.publish()`
(`:3831`) and `app-sh` today (`app-sh/src/bot/orderFee.ts:180-219`
`accrueStreamFee`, keyed by `tradeId` as a monotonic per-order watermark
because Binance's fee is reported **per trade** and must be summed).

### §1.2 Every other venue — the raw field exists, nothing reads it

Six `prepare*OrderMsg()` normalizers each build a plain object literal for
`ExecutionReport` and none references any fee field, even though the raw,
already-typed payload carries one:

| Venue | Normalizer | Fee field(s) on the raw type | Read today? |
|---|---|---|---|
| Bybit | `prepareBybitOrderMsg` (`:4014-4061`) | `cumExecFee: string`, `feeCurrency: string` (`:344,364`) — name says cumulative | No |
| OKX | `prepareOkxOrderMsg` (`:3912-3953`) | `fee`/`feeCcy` (order-level, cumulative by OKX's own convention) **and** `fillFee`/`fillFeeCcy` (latest-fill-only) (`:495-496,523-524`) | No |
| Bitget | `prepareBitgetOrderMsg` (`:4063-4099`) | `fillFee`/`fillFeeCoin` (single) **and** `feeDetail: {feeCoin, fee}[]` (multi-leg) (`:382,393-395`) | No |
| Coinbase | `prepareCoinbaseOrderMsg` (`:3955-4012`) | `total_fees: string` on `WebsocketUserOrder` (`coinbase-advanced-node/dist/client/WebSocketClient.d.ts:225`) — cumulative by name, **no currency field alongside it** | No |
| Hyperliquid | `buildHyperliquidExecutionReport*` (`:4130-4209`) | `hl.Fill.fee`/`feeToken` (per-fill, `@nktkas/hyperliquid` SDK types) | No — not even on the REST-fallback path, which fetches `CommonOrder.fills[].commission` and still drops it (`:4186-4209`) |
| Kraken (spot) | `prepareKrakenOrderMsg` (`:4445-4610`), channel `executions` | `fees: {asset, qty}[]` (trade events only), `fee_ccy_pref: 'fcib'\|'fciq'`, `fee_usd_equiv` (venue-computed USD total, present from `pending_new` on, `0` until a trade) — confirmed against Kraken's own v2 API docs (§3.1) | No |
| Kraken (futures) | `prepareKrakenOrderMsg`, channels `fills`/`open_orders` (`derivativesPrivateV1`, a separate v1-era channel pair — not `executions`) | Unknown — separate from spot, not covered by the v2 `executions` docs; zero `.fee` accesses anywhere in the file | No |
| KuCoin | spot/futures passthrough (`:2196-2231`) | **None** — `WSUpdateOrder`/`WSFuturesOrderMessage` (`@gainium/kucoin-api` types) carry no fee amount at all | N/A — nothing to forward |

### §1.3 What this actually costs today

`app-sh/src/bot/main.ts:convertExecutionReportToOrder` builds/updates the
local `Order` straight from the incoming `ExecutionReport` on every fill
(`main.ts:5552`). For the six venues in §1.2, that message carries no fee,
so the `Order` gets none at that moment. A later REST re-fetch
(`main.ts:getOrder`, `:4452`) can still pick the fee up if the venue's
order-fetch endpoint returns one (most do; Binance is the documented
exception — `app-sh/types.ts:3524-3537`) — but only if and when that
re-fetch happens to run before something needs the number (TP sizing, deal
close). There is no guarantee it does. This spec closes that gap for the
five venues that have a fee field to read (Kraken pending §3.1, KuCoin has
none to give).

## §2 Target behaviour

`ExecutionReport` gains the same fee shape `app-sh`'s own `Order` already
understands — `feePaid?: string`, and either `feeSide?: 'base' | 'quote'`
**or** `feeAsset?: string` (whichever the venue's payload names), plus
`feeBreakdown?: { asset: string; amount: string }[]` for a venue that
reports more than one fee leg on one message. This is a deliberate choice,
not a default: `app-sh/src/bot/orderFee.ts:observedFeeSplit` already
parses exactly this shape (verified — `app-sh/src/bot/orderFee.spec.ts`
covers `feeSide`, `feeAsset`, and `feeBreakdown` cases). Emitting it
directly means `app-sh` needs no new per-venue parsing branch — the
existing normalizer, already proven correct for every venue's fee
convention (side-naming venues vs. ticker-naming venues vs. multi-leg), is
reused unchanged. Binance's `commission`/`commissionAsset`/`tradeId` are
**not renamed or removed** — `accrueStreamFee`'s per-trade-summing
contract stays exactly as is; this spec only adds fields, for other venues.

One more field, new to this spec and not part of `app-sh`'s existing
`Order` shape: **`feePaidUsd?: string`**, forwarded only when the venue
itself computes and reports it — today, only Kraken's `fee_usd_equiv`
(§2.1). `app-sh` spec `006` §1.4/§2.3 is updated to prefer this
venue-supplied number over its own rate lookup when present, since the
venue's own conversion is at least as accurate as anything `app-sh` could
derive from a separately-fetched price table, and removes a rate-lookup
round trip for that leg entirely.

### §2.1 Cumulative vs. per-trade — a real fork, resolved per venue

`observedFeeSplit` expects "the fee for this order, as observed so far" —
a value that can be **assigned**, not summed. That is true directly for a
venue whose own payload is already an order-level running total (Bybit's
`cumExecFee`, OKX's `fee`, Coinbase's `total_fees` all read that way by
name). It is **not** true for a venue whose payload is a per-fill delta
(Hyperliquid's `hl.Fill.fee`, and Bitget's `fillFee` by name) — forwarding
a per-fill delta as if it were the running total would make
`observedFeeSplit` under-report every order that fills in more than one
trade. Per venue:

- **Bybit** — forward `cumExecFee`/`feeCurrency` as-is (§3.2 confirms it
  really is cumulative before this ships).
- **OKX** — forward `fee`/`feeCcy` (the order-level field), not
  `fillFee`/`fillFeeCcy` (§3.2 confirms).
- **Coinbase** — forward `total_fees` as `feePaid`. No currency field
  exists on `WebsocketUserOrder` to pair it with — §4 open question.
- **Bitget** — forward `feeDetail[]` as `feeBreakdown` (already multi-leg,
  already a total per the venue's own multi-fee-currency model), not the
  singular `fillFee` (§3.2 confirms `feeDetail` is the cumulative one).
- **Hyperliquid** — per-fill; needs the same per-order accumulation this
  repo already does for Kraken futures fill totals
  (`krakenFillTotals`, `:602-605`, deduped by `fill_id`) — accumulate by
  `hl.Fill`'s own trade id, keyed per order, and forward the running sum.
- **Kraken (spot)** — `fees[]` is documented as trade-event-only (§3.1);
  Kraken's docs don't state whether it resets per event or accumulates, so
  treat it as **per-fill** and accumulate it the same way as Hyperliquid
  (below) until §3.1's live capture confirms otherwise — under-forwarding
  is the safe default here, not over-forwarding. `fee_usd_equiv`, by
  contrast, is documented as present from `pending_new` (`0`) and
  "updates on trade events" — that reads as an order-level running total,
  not a delta, so forward it as `feePaidUsd` directly, unaccumulated. Two
  different accumulation treatments on the same message is unusual enough
  to call out explicitly in the plan rather than let it fall out of a
  generic per-venue table.
- **Kraken (futures)** — genuinely deferred, separate channel
  (`fills`/`open_orders` on `derivativesPrivateV1`, confirmed distinct
  from spot's `executions`), not covered by the docs that resolved spot.
  Not attempted in this pass.

## §3 Evidence gap — what must be captured before implementation, not assumed

Two things above are inferred from field **names** in already-typed
payloads, not from an observed real message, which is a weaker bar than
this repo's own test convention uses elsewhere (`test/coinbasePartialFill.test.ts`,
`test/krakenFillCumulative.test.ts` both cite real, dated prod payloads).

### §3.1 Kraken spot — the channel and field vocabulary are now known; the accumulation semantics and delivery are not

Confirmed (`src/userStream.ts:3277,3283-3288,4456`): Kraken spot already
subscribes to the v2 `executions` channel (`client.subscribe(['executions',
'balances'], 'spotPrivateV2')`) — not the v1 `openOrders`/`ownTrades` pair.
Kraken's own v2 API docs (supplied directly, not re-derived) document that
channel's `trade`/`filled` `exec_type` events as carrying `fees:
{asset, qty}[]`, `fee_ccy_pref: 'fcib'|'fciq'`, and `fee_usd_equiv`. This
resolves the *channel identity and field names* — a stronger bar than
§3.2's field-name-only inference for OKX/Bybit/Bitget, since it's the
venue's own documentation of this exact channel, not a REST-convention
guess.

**Still not resolved by the docs, still needs a live-captured message
before implementation:**
1. Whether `fees[]` resets per event or accumulates across an order's
   fills — the docs describe the field, not its accumulation behaviour.
   `@siebly/kraken-api` (the WS client this repo uses) has no type
   declaration for this channel's payload at all — confirmed, its own
   event wrapper types the data `any` — so there's nothing to
   cross-check against locally either.
2. Whether this repo's own subscription (`['executions', 'balances']`,
   no `snap_trades`/field-selection params passed) actually receives the
   fee-bearing fields in practice, on this account/setup.
3. That `fee_ccy_pref`/`fee_usd_equiv` really appear on every event as
   documented, and `fees` really stays single-element as Kraken's own
   "expressed in the quote currency only, currently" caveat claims.

Neither of this repo's two Kraken test fixtures (`test/krakenFillCumulative.test.ts`,
`test/krakenSpotBalances.test.ts`) captures an `executions` trade event —
the former is the **futures** `fills` feed (a different channel, §1.2),
the latter is the `balances` channel. No real `executions` payload has
ever been captured in this repo. Before implementing, capture one from
prod logs and confirm items 1-3.

### §3.1a Kraken futures remains fully unknown

Separate from spot in every respect that matters here — different
channels, different API generation (`derivativesPrivateV1` vs.
`spotPrivateV2`), not covered by the docs that resolved spot §3.1. Treat
as its own, unstarted research task.

### §3.2 OKX/Bybit/Bitget "cumulative by name" is an assumption

`fee`/`cumExecFee`/`feeDetail` read as running totals from their field
names and OKX/Bybit's general REST-response convention elsewhere in this
codebase, but no captured WS payload for any of these three has been
inspected to confirm cumulative behaviour specifically on the **private
order-update channel** (as opposed to a REST order-fetch response, which
is a different endpoint). Confirm against a real captured message per
venue before implementation; do not ship on the name alone.

## §4 Open questions

- **Coinbase's fee currency.** `total_fees` has no paired currency field on
  `WebsocketUserOrder`. Coinbase Advanced Trade fees are, by its documented
  fee schedule, always charged in the quote asset — but that is a platform
  convention, not something this message confirms. Emit `feeSide: 'quote'`
  on the assumption, or leave `feeAsset` unset and let `app-sh` assume
  quote-side the way it already must for any venue that only names a side?
  Resolve in the plan.
- **Hyperliquid's per-order fee-accumulation state** — new state alongside
  `krakenFillTotals`, or generalized so both share one mechanism? Resolve
  in the plan.
- **Does a message with a fee but no status change still need to go out?**
  (e.g., a fee-only correction with no new fill.) Not observed in any
  venue's payload shape so far — flag if it turns up during §3 capture,
  otherwise assume no.
