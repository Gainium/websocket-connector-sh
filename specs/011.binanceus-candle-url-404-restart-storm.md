# 011 — the binanceUS candle stream is dialled on `/ws/stream` and 404s

Bug spec (SKILL.md Part 0). Scope: `src/price/binance.ts` — the binanceUS
candle connect URL, and nothing else.

> **Revision 2 (2026-09-18, after a failed post-deploy verification).** Revision
> 1 of this spec asserted a second defect (§1.1b/§1.2b/§2.2: `binanceErrorCb`'s
> family-wide `stopBinance()` + `init()` recovery, claimed to be the mechanism
> by which the US 404 tore down the international feeds) and shipped a scoped
> per-client recovery alongside the URL fix. **That claim was refuted in
> production** and the deploy was rolled back — see §4. The recovery-radius
> change is withdrawn; this revision covers the URL defect only, which stands on
> its own evidence. The international `BINANCE error` volume is a separate,
> still-unexplained condition — §4 records what is and is not known about it,
> and it is deliberately NOT fixed here.

The gate that decides *whether* binanceUS is served (`src/priceConnector.ts`,
spec 010) is correct and out of scope: it is the thing that finally ran this
code, not the thing that is broken.

## §1 Definition

### §1.1 Expected

**§1.1a — the binanceUS candle stream connects to the combined-stream
endpoint.** `connectBinanceCandleStreams` multiplexes up to 200 `@kline_`
streams into one socket via `?streams=a/b/c`. On Binance that payload is only
valid on the **`/stream`** path; **`/ws`** is the raw single-stream path and
takes the stream name in the path, not a query. Every sibling branch in the
same `for` loop already hardcodes the combined form — spot
`wss://stream.binance.com:9443/stream?streams=`, coin-m
`wss://dstream.binance.com/stream?streams=`, usd-m
`wss://fstream.binance.com/market/stream?streams=`. binanceUS must use
`wss://stream.binance.us:9443/stream?streams=` for the same reason.

### §1.2 Actual

**§1.2a — the URL is built from `getWsUrl`, which yields `/ws/stream`.**
`src/price/binance.ts:407-412` (pre-fix):

```ts
this.binanceClientCandleUs.connectToWsUrl(
  `${await this.binanceClientCandleUs.getWsUrl(WS_KEY_MAP.main)}?streams=${wsKey}`,
  WS_KEY_MAP.main,
)
```

The US clients are constructed with `settings.wsUrl =
'wss://stream.binance.us:9443/ws'` (:194-199) — correct for the *ticker*
client, which uses the raw single-stream path. The SDK's `getWsUrl()` returns
that override **and then appends its own `/stream` suffix**
(`binance@3.6.3`), so the candle client connects to:

```
wss://stream.binance.us:9443/ws/stream?streams=btcusdt@kline_1h/...
```

`/ws/stream` is neither endpoint. Binance.US answers **HTTP 404** and the
socket never opens.

### §1.3 Evidence

**Live probe of the real venue and the real SDK** (`node`, read-only, run from
the dev host on 2026-09-18T05:2xZ). The SDK client is constructed with exactly
the settings `getBinanceClient(ExchangeEnum.binanceUS, 'candle')` builds:

```
SDK getWsUrl(main) for the binanceUS client = wss://stream.binance.us:9443/ws/stream
OLD  wss://stream.binance.us:9443/ws/stream?streams=btcusdt@kline_1m  → HTTP 404 Not Found
NEW  wss://stream.binance.us:9443/stream?streams=btcusdt@kline_1m     → STREAMING stream=btcusdt@kline_1m kline_close=77524.39000000
```

So `getWsUrl()` really does return the `/ws/stream` hybrid for this client, and
the two URLs really do differ 404-vs-data at the venue.

**The real code path, driven against the live venue (added 2026-09-18, revision
2 re-verification).** `connectBinanceCandleStreams(true)` run for real off the
prototype, with the real `getBinanceClient(binanceUS, 'candle')` SDK client and
only `connectToWsUrl` wrapped to record the string, for 30s per side:

```
pre-fix  dialled wss://stream.binance.us:9443/ws/stream?streams=btcusd@kline_1m
         → 5× `BINANCEUS error: main {"wsKey":"main"}`, 0 candles in 30s
post-fix dialled wss://stream.binance.us:9443/stream?streams=btcusd@kline_1m
         → 0 errors, closed candles received (BTCUSD 1m, k.x=true)
```

This reproduces the production log line **verbatim** on the pre-fix code, and
shows the reconnect behind the 404 re-dialling the same dead path — which is
what sustains the `BINANCEUS error` rate in §1.3's hourly counts. Note this is
the *US* client's error line (`BINANCEUS`); the international one is
`BINANCE` and is the separate condition in §4. `btcusdt` on this venue is a
thin pair that emitted nothing in 45s — `btcusd` is the liquid one, so a silent
`btcusdt` probe is not evidence of a broken URL.

**Onset is exact, and it is a reachability change, not a code change.** The
`Gainium <-> Binance candle stream connector` boot line gained the venue at
`2026-09-17T19:14:34.697Z` (spec 010's deploy):

```
… streaming: bybit,binance,okx,kucoin,bitget,hyperliquid,kraken,coinbase,binanceUS | NOT streaming: (none)
```

`BINANCEUS error: main` in that process's live + archived pm2 error logs, per
hour: 0 before `2026-09-17T18` (7 unrelated `BINANCEUS` substring hits across
90 days), then **68** in the deploy hour, then **77–92 every hour, unbroken**,
through `2026-09-18T04:28:48Z`. The very first one is
`2026-09-17T19:14:35.815Z` — 1.1s after the boot line.

**The subscriptions are real and the fix is on the live path.** The same
process logs `Received candle request … binanceUS 1h` for `SOLUSDT` (127×) and
`LINKUSDT` (68×), re-requested at every boot including `2026-09-18T04:29`. So
`subscribedCandlesMap.get(binanceUS)` is non-empty and the `us` branch of
`connectBinanceCandleStreams` really does run.

**Caveat on a signal revision 1 relied on.** Revision 1 cited "`BINANCEUS …
opened` appears in 0 of 92 files" as proof the socket never opened. That is
true but **worthless as evidence**: `BINANCE candle opened`, `BINANCE ticker
opened` and `BINANCEUS ticker opened` are *also* 0 in that process, including
for the international candle streams that demonstrably work. The `open`
callback simply does not fire on the `connectToWsUrl` path. Do not reuse it.

### §1.4 User-visible consequence

Bots trading binanceUS pairs get no closed-candle stream: the candle
subscription is accepted and the socket that would serve it 404s, so
indicator/candle-close driven checks fall back to the 2.5-minute REST price
poll, indefinitely. That is the same degradation spec 010 set out to end — its
gate fix made the venue reachable, and this URL is what still stops it short.
Two pairs (SOLUSDT, LINKUSDT at 1h) are subscribed in production.

## §2 Assumption (hypothesis)

**§2.1** `getWsUrl(WS_KEY_MAP.main)` is the wrong builder for a combined
stream. Hardcoding `wss://stream.binance.us:9443/stream?streams=` — exactly as
the three sibling branches already do — makes the socket open.

**Origin: latent, and specifically an incomplete earlier fix.** The line's
current text is `42366161` (2025-07-02), but the *divergence* was created by
`7b2a652` — "v1.5.3: Fixed Binance new urls", 2026-04-27 — which converted the
coin-m, usd-m and spot candle branches from
`getWsUrl(...)+'?streams='` to their hardcoded combined-stream URLs **and
skipped the `us` branch in the same `if/else`**. It stayed dormant for five
months because `isUs` was always `false`; spec 010's gate fix is what executed
it for the first time.

## §3 Out of scope

- The `isBinanceUS` gate (spec 010). It is correct and stays as-is: the answer
  to "binanceUS 404s" is to fix the URL, never to re-dark the venue.
- `settings.wsUrl = 'wss://stream.binance.us:9443/ws'` (:194-199). It is right
  for the ticker client, which is the only other consumer of the US settings.
- The ticker-side `subscribeSpotAllMini24hrTickers()` path for binanceUS — it
  uses the SDK's own subscribe helper, not `connectToWsUrl`, and is unaffected.
- **`binanceErrorCb`'s family-wide recovery radius — see §4.**

## §4 The international `BINANCE error` volume — open, not addressed here

Revision 1 claimed this was collateral damage from the US 404 (each US
exception firing `stopBinance()` + `init()`, tearing down the healthy
international clients). **That claim is withdrawn.** What the logs actually
support:

- **The two onsets do not coincide.** The first `BINANCEUS error` is
  `2026-09-17T19:14:35.815Z`, ~1s after the venue became reachable. The first
  international `BINANCE error` of the episode is `2026-09-17T20:43:56.629Z` —
  **89 minutes later**. A handler that fires a family-wide teardown on *every*
  US exception would have produced international exceptions within seconds, not
  after 89 minutes and ~130 US exceptions.
- **The rates are inconsistent with lockstep.** Revision 1 read a 40-line
  window as "US → intl → US → intl, seconds apart" and generalised. Per hour the
  two run at roughly 85 (US) against 66–1057 (intl); they are not 1:1.
- **Revision 1's "72% of intl errors fall in the nine hours after the deploy"
  was computed from a `-n 2000`-truncated read** that silently dropped archived
  files. It should not be relied on.
- **The post-deploy measurement refuted it directly.** With the URL corrected
  and `BINANCEUS error` at 0, the international volume did not fall.
- **The current silence proves nothing either way.** International errors stop
  at `2026-09-18T04:34:00Z` and there have been none since. But the rollback
  did **not** restart this process: `pm2` reports `Gainium <-> Binance candle
  stream connector` and `… price stream connector` still up since
  `2026-09-18T04:29:3xZ` on `v2.13.17` — the build containing revision 1's
  changes — because the ship path restarts only `userStream` (the candle and
  price ecosystems need their own `do -s` run, per the service CLAUDE.md's
  two-checkout topology). So the quiet window is under the *unrolled-back*
  binary, and attributing it to either the fix or the rollback would be a
  second unfounded inference.

What would settle it: the `exception` payload is logged as
`JSON.stringify(data.error ?? data)` and comes out as `{"wsKey":"main"}` —
the SDK's actual error is not captured, so no log line in existence says *why*
an international socket faulted. Capturing that payload (a log-only change) is
the prerequisite for any fix here. Also worth checking: the `us`/intl branches
all pass the **same** `WS_KEY_MAP.main` for every 200-stream chunk, so a
multi-chunk international subscription re-uses one wsKey N times — which would
produce exactly the observed "~1.0s spacing" bursts (the per-chunk
`await sleep(1000)`). That is a hypothesis, not a finding; it has not been
reproduced.

This belongs in its own issue. It is not fixed by this spec.
