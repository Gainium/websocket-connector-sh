# 020 — a Hyperliquid cancel with a shrunk size is reported as partly filled

Bug spec (SKILL.md Part 0). Scope: `src/userStream.ts`
(`prepareHyperliquidOrder`, `buildHyperliquidExecutionReport`) and
`src/utils/hyperliquidFillPark.ts` (fill-history lookup).

## §1 Definition

### §1.1 Expected

An execution report for a Hyperliquid order that ended without filling
(`canceled`, `reduceOnlyCanceled`, `marginCanceled`, … — any status other than
`open` and `filled`) carries an executed quantity, quote and fee equal to the
order's real fills on the venue: zero when it has none. Spot and perps alike.

### §1.2 Actual

`buildHyperliquidExecutionReport` sets the executed quantity to
`origSz − sz` from the `orderUpdates` frame. When no `userFills` were buffered
for the cloid it keeps that number and prices it at `limitPx`. Hyperliquid can
lower `sz` on a resting order without any fill (seen on a reduce-only order), so
the cancel is relayed as `CANCELED` with `totalTradeQuantity = origSz − sz` and
no fee. Downstream that quantity is booked as executed, so the deal's base
balance no longer matches the position, and a later full close sells too little.

## §2 Evidence

- Production `HL-user-stream-worker`, one reduce-only grid SELL (HYPE perp):
  - open: `sz 1.02, origSz 1.02, status open`;
  - cancel: `sz 0.97, origSz 1.02, status canceled, fills:[]`;
  - no `userFills` frame for that cloid or oid in any log archive.
- Hyperliquid's own `info` endpoint, read for the same account:
  - `orderStatus` for the oid: `canceled`, `sz 0.97`, `origSz 1.02`;
  - `userFillsByTime` over the order's lifetime: 2 fills, neither for that oid.
  So the venue confirms zero executed; the 0.05 relayed as filled never traded.
- The order row downstream holds `executedQty ≈ 0.05` with no fee and no fills,
  and the deal's books lead the exchange position by the same 0.05.
- Origin: latent — `origSz − sz` has been the executed quantity since
  Hyperliquid support was added; the later park-and-retry change only moved it.

## §3 Assumption

`origSz − sz` is not evidence of a fill. Hyperliquid's fill history
(`userFillsByTime`, filtered by `oid`) is. Checking it only when the update is
non-filled, terminal, shows `origSz − sz > 0`, and has no buffered fills keeps
the extra request to that rare case.

## §4 Requirements

- **§4.1** Non-filled terminal update, `origSz − sz > 0`, nothing buffered, and
  the history holds no fill for the oid → executed quantity, quote 0, no fee.
- **§4.2** Same, history holds fills for the oid → executed quantity, quote, fee
  and fee asset are the sum of those fills (spot and perps).
- **§4.3** The history lookup fails, times out, or is truncated (more pages
  than the cap) → a failed lookup is not evidence either way, so nothing is
  reported for that order yet and a warning naming the cloid, oid and attempt
  is logged. The lookup is retried off the batch with doubling backoff
  (default 3 retries, 4s base ≈ 30s; `HL_FILL_HISTORY_RETRIES`,
  `HL_FILL_HISTORY_RETRY_DELAY_MS`); the first success emits the §4.1/§4.2
  report. Only when every attempt fails is the pre-020 `origSz − sz` report
  emitted, with an error naming the cloid, oid and attempt count. A replay of
  the same cancel while its retry is pending is not reported again. The other
  orders in the batch are emitted immediately.
- **§4.4** Unchanged: `filled` updates (buffer → park → REST), `open` updates,
  terminal updates with buffered fills, and terminal updates with
  `origSz − sz = 0` make no history request.
- **§4.5** The lookup pages forward over `[order.timestamp, statusTimestamp + slack]`
  (fills arrive oldest first, at most 2000 per page), de-duplicates by `tid`,
  and filters by `oid`.

## §5 Out of scope

Existing order and deal rows already written with a phantom quantity are not
repaired here. Hyperliquid's fill history holds only an account's most recent
10000 fills; an order older than that window can return no fills when it had
some — accepted, it needs an account with >10000 fills since the order was placed.
