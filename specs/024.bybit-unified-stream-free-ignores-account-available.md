# 024 — Bybit `wallet` push: unified `free` ignores the account's available balance

## 1. Definition

### 1.1 — expected

For a Bybit `wallet` push on a UNIFIED account, `prepareBybitOutboundAccountInfo`
streams as `free` for USDT and USDC no more than the account-level
`totalAvailableBalance`, converted from USD into the coin (`usdValue / equity`,
1 when missing). This is the same rule as the REST balance
(exchange-connector-sh spec 052).

### 1.2 — partition kept

`free + locked` stays the coin's wallet balance; what the cap removes from
`free` moves to `locked`.

### 1.3 / 1.4 — never raises; out of scope

The cap only lowers `free`; a negative figure clamps it to 0. `free` is
unchanged when the figure is absent or not a number, for other coins, and for
non-UNIFIED accounts (classic `SPOT` / `CONTRACT`).

### 1.5 — actual (before)

`free = free + walletBalance - (locked + totalOrderIM + totalPositionIM)`.
Wallet balance excludes unrealized PnL, and the per-coin margin fields can be
empty, so each push wrote a `free` above what the venue would let the account
spend over the row the REST refresh had written.

## 2. Evidence

The stream writes the same `balances` rows the REST poll does (main-app
`processBalanceUpdate`, `outboundAccountPosition`), so a REST-only fix would be
undone by the next push. `totalAvailableBalance` is a documented field of every
`wallet` topic account entry.

## 3. Assumption

As REST spec 052 §3: the venue gates a new order on a unified account on
`totalAvailableBalance`.

## Invariants

Owned by main-app `specs/invariants/balances.invariants.json`
(`balances.bybit-linear-not-enough-balance-but-free-covers-it`).
