# 017 — OKX stream fees reach the platform as a cost, not a signed charge

Bug spec (Definition / Evidence / Assumption). Same mechanism as
[016](016.bitget-stream-fee-sign.md), on a different venue.

## §1 Definition

§1.1 **Expected.** When an OKX private-stream order update carries a
negative order-level `fee` (OKX's way of stating a charge), the
`ExecutionReport` this repo publishes states it as the **cost** the venue
charged: a positive `feePaid`, keeping the venue's own digits, with
`feeAsset` = `feeCcy`. main-app then books it, e.g. a USDT fee on a
`BTC/USDT` order as `{base: 0, quote: 0.05}`, plus one fee-ledger leg.

§1.2 **Actual.** `prepareOkxOrderMsg` forwards `data.fee` unchanged
(`feePaid: '-0.05'`). main-app's `streamFeeFields` assigns it onto the
order. `observedFeeSplit` then returns `null`, so the order falls back to
the estimate, and `observedFeeLegs` returns `[]`. A stream update that
arrives after the REST poll replaces the usable REST fee (exchange-connector
`normalizeOrderFee` takes the magnitude) with this unusable one.

§1.3 **Unchanged.** A non-negative OKX `fee` (zero, or a positive value,
which on OKX may be a rebate) is forwarded byte-for-byte, exactly as today.
The order-level `fee`/`feeCcy` is still the field read, never the
per-fill `fillFee`. Bitget's behaviour from 016 is unchanged.

## §2 Evidence

§2.1 Code path: `src/userStream.ts` `prepareOkxOrderMsg` →
`feePaid: data.fee`. `test/venueFeeForwarding.test.ts` pins `'-0.05'` as
the forwarded value.

§2.2 main-app core `src/bot/main.ts` `Object.assign(order,
streamFeeFields(msg))`, then `src/bot/orderFee.ts` `observedFeeSplit`
(`!(amount > 0)` → `null`) and `src/bot/feeLedger.ts` `observedFeeLegs`
(skips `amount <= 0`).

§2.3 Persisted prod state (read-only, orders created in the 3 days to
2026-10-04): 403 `okx` and 8 `okxLinear` orders store a negative `feePaid`,
e.g. a LIMIT SELL of 7.2819 INJ at 7.431 USDC with `feePaid
'-0.04328943912'`, `feeAsset 'USDC'`, which is 0.08% of the notional (a normal
maker charge). exchange-connector's OKX REST mapper (`okx/index.ts`,
`normalizeOrderFee(order.fee, order.feeCcy)`) never emits a negative value,
so these could only have been written by the stream path: the path runs
and its output is persisted. The connector's own `getUserFees` for OKX
also flips the sign (`maker * -1`), which is the same convention.

## §3 Assumption (hypothesis)

The stream mapper is the only place the sign is lost: forwarding a
negative OKX `fee` as its magnitude makes main-app's existing fee
processing book it, with no main-app change.
