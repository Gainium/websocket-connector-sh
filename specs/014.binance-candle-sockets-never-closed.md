# Spec 014 — Binance candle sockets are never closed, so every re-dial leaks a live stream

Bug spec (Definition / Evidence / Assumption). Companion plan:
[`plans/014.binance-candle-sockets-never-closed.md`](../plans/014.binance-candle-sockets-never-closed.md).

Spun off from spec 013 (the Binance exception restart storm) while reproducing
it: 013 stopped the *rate* of restarts, this one is why a restart does not
actually replace anything.

---

## 1. Definition

### 1.1 Expected

`closeBinanceCandleStream(us, futures)` closes the candle sockets its branch
previously dialled. After it returns:

- **1.1a** No further candle frames reach `binanceCandleCb` → `cbWsTrade` from
  those sockets, so nothing further is published to the Redis
  `{symbol}@{exchange}@{interval}Candle` channel or to the `archiveCandleWrite`
  RabbitMQ queue from the superseded connection.
- **1.1b** Every socket the branch dialled has left `readyState === 1` (OPEN).
- **1.1c** `connectBinanceCandleStreams()` — which calls
  `closeBinanceCandleStream()` as its first act after the debounce — therefore
  **replaces** the branch's sockets rather than adding to them. The number of
  live candle sockets for a branch is bounded by its chunk count, whatever the
  restart rate.
- **1.1d** `stopBinance()`, which recreates all eight clients through
  `getBinanceClient(…, current)`, likewise leaves no socket of the outgoing
  client running.

### 1.2 Actual

None of 1.1a–1.1d hold. `closeBinanceCandleStream()` and `getBinanceClient()`
close via `client.closeAll(false)`, which closes only sockets the SDK has
registered in its own `wsStore` — and the candle branches dial sockets the SDK
never registers (§3.1). `closeAll()` is a no-op on them: they stay OPEN and keep
publishing closed candles for the lifetime of the process.

Each re-dial therefore **adds** a candle socket per chunk instead of replacing
one. Under the restart storm of spec 013 that was one leaked, still-publishing
candle socket per branch per restart cycle, each one emitting duplicate closed
candles into the shared market-data channels.

### 1.3 Also explained by the same cause (not itself the defect)

`BINANCE candle opened` / `BINANCEUS candle opened` never appear in the candle
connector's logs. `binanceOpenCb` is registered on the `open` event, and the SDK
emits `open` only when the connection state for the key is `CONNECTING`
(`binance/lib/util/BaseWSClient.js` `onWsOpen`) — a state only `connect()` sets.
Spec 011 §1.3 recorded this as a caveat; it is a symptom of §3.1. Any triage
using "no `opened` line" as evidence that a socket failed to open is reading an
artefact.

## 2. Evidence

### 2.1 Live venue, real connector code

Harness: `Object.create(BinanceConnector.prototype)`, a real
`BinanceWSClient`, the real `connectBinanceCandleStreams(false)` against
`wss://stream.binance.com:9443/stream?streams=…` for three 1m kline streams,
then the real `closeBinanceCandleStream(false)`. Public market data, read-only.

```
messages received:            16
exceptions:                   0
sockets dialled:              1
wsStore keys:                 ["main"]
wsStore holds a socket:       ["NO-WS"]      <-- registered key, no socket
readyState before close:      [1]
--- closeBinanceCandleStream(false) ---
readyState right after close: [1]
messages after close:         16  (total 32)
readyState 12s after close:   [1]            <-- still OPEN
RESULT: LEAKED — socket still open and/or still publishing
```

`wsStore keys: ["main"]` with `NO-WS` is the defect in one line: the key exists
(the SDK's `onWsOpen` sets a connection *state* for it) but no socket was ever
stored against it, so `close()`'s `getWs(wsKey)` is `undefined` and its
`ws?.close()` does nothing.

### 2.2 SDK source, `binance@3.6.3` (the resolved version of the pinned `^3.1.9`)

`lib/util/BaseWSClient.js`:

- `connect(wsKey, customUrl)` → `const ws = this.connectToWsUrl(url, wsKey); this.wsStore.setWs(wsKey, ws)`
- `connectToWsUrl(url, wsKey)` → builds the socket, wires its handlers, returns
  it. **No `setWs`.**
- `closeAll(force)` → `this.wsStore.getKeys().forEach((key) => this.close(key, force))`
- `close(wsKey, force)` → `const ws = this.getWs(wsKey); ws?.close()`

### 2.3 The same SDK's *legacy* client still stores it

`lib/util/../websocket-client-legacy.js:109` — `this.wsStore.setWs(wsRefKey, ws)`
inside `connectToWsUrl`. That is the v2 behaviour this code was written against
(§4).

## 3. Assumption (root-cause hypothesis)

### 3.1 The cause

`connectBinanceCandleStreams()` dials all four candle branches through the SDK's
**private** `connectToWsUrl(url, wsKey)` (`src/price/binance.ts`, the four
`//@ts-expect-error connect to wsUrl is private` sites). Under `binance@3.x`
that method does not register the socket in the SDK's `wsStore`, and the
connector keeps no reference of its own — so the returned socket has **no
handle anywhere** once the expression returns. `closeAll(false)` iterates the
store; the store has nothing to close.

### 3.2 Why `connect()` is not the answer

Moving to `client.connect(wsKey, customUrl)` would restore the registration, but
the SDK refuses a second `connect()` on a `wsKey` that is already open
(`'Refused to connect to ws with existing active connection'`), and every chunk
of a branch shares one key — so every chunk past the first would be silently
dropped. Giving each chunk its own synthetic key is worse: on any unintentional
close the SDK reconnects by calling `connect(wsKey)` with no custom URL, which
routes into `getWsURLSuffix(wsKey)`; that function `throw`s `Unhandled WsKey`
for anything outside `WS_KEY_MAP`, `connect()` catches it into
`parseWsError(…)`, and `parseWsError` unconditionally re-emits `exception` —
straight back into `binanceErrorCb`, i.e. a self-feeding restart cycle at the
reconnect interval. `WS_KEY_MAP` offers three spot keys; a branch has one chunk
per 200 streams.

The connector must therefore keep its own handle on what it dialled.

### 3.3 Required behaviour of the fix

- **3.3a** Every socket dialled by `connectBinanceCandleStreams()` is retained,
  per client, until it is closed.
- **3.3b** `closeBinanceCandleStream(us, futures)` closes exactly the retained
  sockets of that branch's client, and forgets them.
- **3.3c** `getBinanceClient(exchange, type, current)` does the same for the
  outgoing client, so `stopBinance()` leaves nothing running.
- **3.3d** Closing detaches the SDK's own handlers from the socket first, so the
  teardown does not publish (`onmessage`), does not raise an `exception` into
  `binanceErrorCb` (`onerror`) — which under spec 013 would start a restart
  cycle — and does not trip the SDK's unintentional-close recovery
  (`onclose` → `reconnectWithDelay` → a stream-less socket on the shared key).
- **3.3e** `closeAll(false)` is still called, because the SDK legitimately holds
  sockets of its own on those clients (anything its reconnect path created).
- **3.3f** The dial path itself is unchanged: same URLs, same wsKeys, same
  chunking, same one-second spacing. No chunk may be lost (§3.2).
- **3.3g** An `opened` line is logged per dialled candle socket, through the
  existing `binanceOpenCb`, so §1.3 stops being an evidence trap and chunk
  delivery is observable in production.

### 3.4 Not in scope

The restart *radius* (a fatal exception still recreates the whole Binance
family) and the restart *rate* are spec 013's, unchanged here.

## 4. Origin

**Regression**, introduced by `4236616` "chore: bump version to 1.0.5"
(2025-07-02), which moved the pinned SDK from `binance@^2.15.22` to `^3.0.0`.

Before it, the candle branches called
`connectToWsUrl(url, wsKey, forceNew)` where `wsKey` was the chunk's own stream
list — a distinct key per chunk — and the v2 client's `connectToWsUrl` **did**
`wsStore.setWs()` (§2.3), so `closeAll()` closed every chunk correctly. The
bump rewrote the call sites onto `WS_KEY_MAP.main`/`coinm`/`usdm`, dropped the
third argument, and left the private-method dial in place; v3's rewritten
`BaseWSClient` had moved `setWs` into `connect()`. The commit's own message
describes it as "code compatibility changes" — the compatibility hole is this
one. `git blame src/price/binance.ts` puts the `connectToWsUrl` calls at
`38b5d4f` (2025-06-26, under v2) and their `WS_KEY_MAP.*` arguments at
`4236616`.

The leak has been latent-but-bounded since: it costs one socket per branch per
re-dial, and re-dials were rare until spec 013's storm made them continuous.
