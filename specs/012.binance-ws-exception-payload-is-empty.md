# 012 — the Binance `exception` handler logs an empty payload

Bug spec (SKILL.md Part 0). Scope: `src/price/binance.ts` — the *log line*
`binanceErrorCb` emits, and nothing else.

The `stopBinance()` + `init()` restart in the same handler is a separate,
separately-filed defect (unguarded family-wide restart on every exception). It
is deliberately **not** touched here — spec 011 revision 2 records that the last
attempt to change the recovery radius in the same commit as another fix was
refuted in production and rolled back. See §5.

## §1 Definition

### §1.1 Expected

When a Binance websocket faults, the error line names **why**: the underlying
message (`Unexpected server response: 404`, `connect ECONNREFUSED …`, a close
code/reason), alongside the `wsKey` the fault happened on. The line stays on one
line and keeps its `${EXCHANGE} error: ${wsKey} ` prefix, which is what every
existing log grep and the `/findings` collectors match on.

### §1.2 Actual

`src/price/binance.ts:168-179`:

```ts
private binanceErrorCb(e: ExchangeEnum) {
  return (data: any) => {
    logger.error(
      `${e.toUpperCase()} error: ${`${data.wsKey}`.slice(0, 100)} ${JSON.stringify(data.error ?? data ?? '')}`,
    )
    this.stopBinance()
    this.init()
  }
}
```

The payload serialises to `{"wsKey":"main"}` — no message, no code, no close
reason, no URL. The line is informationally empty beyond "something faulted on
wsKey main".

## §2 Evidence

### §2.1 Production

Service `Gainium <-> Binance candle stream connector`, sampled by triage on
2026-09-18: **1999 of 2000** `BINANCE|BINANCEUS error:` lines carry exactly
`{"wsKey":"main"}`. Since that is the `?? data` arm of the nullish chain, it
also proves `data.error` is nullish in essentially every real event — a fix that
only serialises `data.error` better would change nothing.

### §2.2 Reproduced locally against the real SDK

`binance@3.6.3` driven against a local HTTP server that answers 404 to the
upgrade, with the production log expression applied verbatim, printed:

```
BINANCE error: main {"wsKey":"main"}
```

byte-identical to production. `connect ECONNREFUSED` and a DNS failure produce
the same line. The payload's real shape, read out in the same probe:

| own string keys | own symbol keys |
|---|---|
| `wsKey` | `Symbol(kTarget)`, `Symbol(kType)`, `Symbol(kError)`, `Symbol(kMessage)` |

`Symbol(kMessage)` held `Unexpected server response: 404` and `Symbol(kError)`
the `Error` itself. `data.message`, `data.error` and `data.wsUrl` were all
`undefined`.

A second blind shape exists alongside it: the SDK's non-transport `exception`
sites emit `{ wsKey, functionRef, error: <Error> }`, and `JSON.stringify` of an
`Error` is `{}` because `name`/`message` are non-enumerable — so those lines
print `BINANCEUSDM error: usdm {}`.

## §3 Assumption (root-cause hypothesis)

The information is destroyed by an **object spread in the SDK**, before our
handler ever sees it. `binance/lib/util/BaseWSClient.js` `parseWsError` emits

```js
this.emit('exception', { ...error, wsKey })
```

and `error` is the `ws` library's `ErrorEvent`. In `ws@8`, `ErrorEvent`'s
`message`/`error`/`type`/`target` are **prototype getters** (`CloseEvent` adds
`code`/`reason` the same way) backed by symbol-keyed own slots. An object spread
copies own enumerable properties — the symbol slots survive, the prototype
getters do not — and `JSON.stringify` ignores symbol keys. Hence
`{"wsKey":"main"}`.

Therefore the payload is not empty, it is *unreachable by property name*: the
handler must read the orphaned symbol slots as well as ordinary properties, and
must treat an `Error` value as its `name`/`message` rather than as `{}`.

## §4 Required behaviour of the fix

- **§4.1** The line carries the underlying reason for a transport fault
  (`message`, and the close `code`/`reason` when the payload is a `CloseEvent`),
  plus the dialled URL when one is recoverable.
- **§4.2** The ordinary own properties the SDK's other `exception` sites do
  carry (`message`, `error`, `code`, `functionRef`, …) are still reported, and
  an `Error` among them reports its message rather than `{}`.
- **§4.3** The prefix `${EXCHANGE} error: ${wsKey} ` and the single-line shape
  are unchanged.
- **§4.4** Credentials are never serialized into the line. The SDK's
  `exception` payloads include `tryWsSend`-style frames and request options, and
  `src/utils/redact.ts` exists precisely because those carry live keys; its
  §-comment states the rule as "never `JSON.stringify` an exchange error — use
  `safeStringify`". The current line breaks that rule.
- **§4.5** A payload we cannot improve on degrades to today's output rather than
  to something worse.

## §5 Out of scope

- `this.stopBinance(); this.init()` — the unguarded, uncoalesced family-wide
  restart on every `exception`. Real, measured (≈1,808 restart cycles/day), and
  filed separately. Changing it here would repeat spec 011 revision 1's mistake
  of bundling a recovery-radius change with an unrelated fix.
- `bybit.ts` / `okx.ts` / `kucoin.ts`, which drive the same `ws` library and are
  likely to have the same blind shape. Not measured here, so not claimed.
- `binanceOpenCb` — `logger.info`, not an error path.
