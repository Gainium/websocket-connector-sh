# 004 — Binance user-stream order ids above 2^53 lose their low digits

Bug spec. Companion to `exchange-connector-sh` spec `004.binance-order-id-precision-loss.md`,
which fixed the same defect on the REST transport (shipped 2026-09-05, deploy #183). This is the
websocket half: the same venue field, arriving over the user data stream instead of over REST.

## 1. Definition

### 1.1 Expected

For every Binance user-stream order event, the exchange order id that this connector publishes on
the Redis account channel is the **exact** id Binance put on the wire.

- §1.1.1 A futures `ORDER_TRADE_UPDATE` frame carrying `o.i = 8389766269723522123` publishes
  `orderId` whose decimal text is `8389766269723522123`.
- §1.1.2 A spot `executionReport` frame carrying `i = 4293153` publishes `orderId` `4293153`,
  as a JSON **number**, exactly as it does today.
- §1.1.3 Two frames carrying two different venue ids publish two different `orderId` values.

### 1.2 Actual

Any id above `Number.MAX_SAFE_INTEGER` (2^53 - 1 = 9007199254740991) is published with its low
digits replaced by zeros. `8389766269723522123` is published as `8389766269723522000`. Because the
rounding is many-to-one, distinct venue orders collapse onto a single published id (§1.1.3 fails).

Every one of these 19-digit ids ends in `000`. Binance does not issue ids in multiples of 1000;
that suffix is the IEEE-754 double it was rounded to.

### 2.2 Production database — how far it has spread

Read-only aggregate over prod `orders`, restricted to `exchange: 'binanceUsdm'` and
`orderId: /^[0-9]{19,}$/`:

| measure | value |
|---|---|
| rows with a 19+ digit stored `orderId` | 743 |
| of those, ending in `000` (the rounding signature) | **741** |
| distinct users holding one | **6** |
| collision groups (one `orderId`, >1 row) | **22** |
| rows inside a collision group | **52** |
| collision groups whose rows have **different** `clientOrderId`s | **22 of 22** |

All 22 collisions are genuinely different orders — different client order ids — sharing one stored
exchange order id. `orders.orderId` is `RequiredString` in the mongoose schema
(`main-app-sh core/src/db/schema.ts:702`), so the already-rounded number is stringified verbatim on
write and the true digits are not recoverable from our own data.

### 2.3 Traced code path

`__repro706.ts` drives the real vendor client (`binance@3.5.5`) exactly as production does — the
frame goes into `WebsocketClient.onWsMessage()`, the listener is the one installed at
`userStream.ts:1916`, and the mapper is the real `convertFutures`:

```
wire  : ..."i":8389766269723522123...
parsed: orderId = 8389766269723522000  (typeof number)
exact?: false
redis payload = {"orderId":8389766269723522000,"clientOrderId":"D-BO-abcdef"}
```

The same harness with `i = 4293153` round-trips exactly, confirming the loss is specific to values
above 2^53.

## 3. Assumption (hypothesis, not fact)

The truncation happens **inside the vendor SDK, before any Gainium code runs**.

`WebsocketClient.resolveEmittableEvents()` (`binance/lib/websocket-client.js:502`) calls
`parseRawWsMessage(event, this.options)`, which at
`binance/lib/util/websockets/websocket-util.js:798-800` does a bare `JSON.parse(event)` unless
`options.customParseJSONFn` is supplied. `JSON.parse` has no representation for an integer above
2^53 and returns the nearest double.

Therefore `core/src/utils/binance.js:228` (`orderId: m.o.i`) is **not** the defect — it faithfully
copies a field that is already rounded. Any fix applied at or after that line is applied to data
whose low digits no longer exist.

Corollary the test must show: the failure has to be visible when the frame enters the vendor client
as **raw text**, and must disappear only when the parse itself is changed. A test that hands
`convertFutures` an already-parsed object cannot fail for this reason and would not test the
assumption.

## 4. Scope

### 4.1 In scope

- §4.1.1 The Binance user-stream clients constructed in `userStream.ts` (spot, binanceUS,
  binanceUsdm, binanceCoinm, and the Ed25519 WS-API spot client).
- §4.1.2 The wire key `i`, which is the order id in both `ORDER_TRADE_UPDATE` (`o.i`) and
  `executionReport` (`i`). No other user-stream field is a venue integer id that can exceed 2^53.

### 4.2 Out of scope

- §4.2.1 **No backfill.** The 741 rounded rows cannot be repaired locally — the lost digits exist
  only at Binance. Re-fetching them is separate work.
- §4.2.2 The price/candle connectors (`src/price/binance.ts`). They construct their own clients and
  carry no order ids.
- §4.2.3 The REST transport, already fixed in `exchange-connector-sh` (deploy #183).

### 4.3 Invariants that must not move

- §4.3.1 An id at or below 2^53 stays a JSON **number** with the same value it has today. This is
  the overwhelming majority of orders and the only way to bound the blast radius.
- §4.3.2 Digits appearing inside a JSON **string** value — a `clientOrderId` such as
  `D-BO-9CLgYh80pabXS6hhObOG`, a venue error `msg` — are never rewritten.
- §4.3.3 A frame that is not JSON, or is truncated, behaves **exactly as `JSON.parse` does today**
  — including throwing. Corrected at gate 4: the first draft said the parser must not throw, which
  is wrong. `resolveEmittableEvents` wraps the parse in a `try` and its `catch`
  (`binance/lib/websocket-client.js:743`) emits an `exception` event carrying the raw frame, which
  `userStream.ts:1956` handles. Swallowing the error would instead return a string as the parsed
  event, producing an "Unhandled non-string event type" error log, a bogus `message` emit, and the
  silent loss of that `exception` signal. Matching `JSON.parse` is what keeps the vendor's error
  path identical.
- §4.3.4 Non-order frames (`ACCOUNT_UPDATE`, `outboundAccountPosition`, `balanceUpdate`,
  `MARGIN_CALL`, `ACCOUNT_CONFIG_UPDATE`) are byte-for-byte unchanged.
- §4.3.5 Every other venue's user stream (bybit, bitget, okx, kucoin, kraken, coinbase,
  hyperliquid) is untouched.

## 5. Consumer contract

The published payload's `orderId` becomes a **string** for ids above 2^53 (it is already
`number | string` in `userStream.ts:264`'s `ExecutionReport`). Checked against main-app, the only
consumer:

- §5.1 `orders.orderId` is `RequiredString` in mongo — the field is *already* stored as text, so a
  string arrives in its declared type rather than being coerced from a wrong number.
- §5.2 `core/src/bot/main.ts:5117` writes `` `${msg.orderId}` `` and `:5241` assigns
  `order.orderId = msg.orderId` into a `string | number` field. Both are correct for a string.
- §5.3 The two strict comparisons on this field (`main.ts:5179`, `:5185`) are inside a
  `this.krakenSpot` branch, unreachable for Binance. They compare against values stored as strings,
  so a string is in fact *more* likely to match than today's number.
- §5.4 `uniqueMessageId` is produced by this connector, logged at `userStream.ts:3856`, and read by
  nothing in main-app. Its text changes (the tail becomes the true id); nothing depends on it.
- §5.5 `OrderUpdate.orderId` in `main-app-sh core/types.ts:3487` is declared `number` and becomes
  documentation-stale. Runtime is unaffected (§5.1-5.3) and main-app still compiles, because the
  connector is not a compile-time dependency. Correcting that declaration is main-app-sh work.
