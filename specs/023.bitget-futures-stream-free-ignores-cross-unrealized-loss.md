# 023 — Bitget classic futures account push: `free` ignores the open cross loss

## 1. Definition

### 1.1 — expected

For a classic Bitget USDT-M / USDC-M `account` push,
`prepareBitgetFuturesOutboundAccountInfo` streams as `free` no more than the
venue's `maxOpenPosAvailable`. That is the amount the venue accepts for a new
position, and in cross mode it nets the open positions' unrealized loss out.
This is the same rule as the REST balance (exchange-connector-sh spec 051).

### 1.2 — partition kept

`locked = equity - unrealizedPL - free`, so `free + locked` stays the wallet
balance.

### 1.3 / 1.4 — never raises; missing figure

The cap only lowers `free`. If `maxOpenPosAvailable` is absent or not a
number, `free` stays `available`, as before. A negative figure clamps to 0.

### 1.5 — actual (before)

`free = available`. That figure does not net the open cross loss out. Each
push overwrote the balance row the REST refresh had written, so a bot with
losing cross positions saw a free balance the venue would not let it spend.

## 2. Evidence

The stream writes the same `balances` rows the REST poll does (main-app
`processBalanceUpdate`, `outboundAccountPosition`). A REST-only fix would
therefore be undone by the next push. Push fields are per Bitget's v2 futures
Account Channel: `available`, `maxOpenPosAvailable`, `equity`,
`unrealizedPL`.

## 3. Assumption

The venue gates a new order on `maxOpenPosAvailable`, the push counterpart of
the REST `crossedMaxAvailable`. COIN-FUTURES pushes are out of scope, matching
REST spec 051 §3.

## Invariants

Owned by main-app `specs/invariants/balances.invariants.json`
(`balances.bitget-usdm-not-enough-balance-but-free-covers-it`).
