# 022 — Kraken spot candle reconnect replays every stored flush at once

Bug spec (Definition / Evidence / Assumption).

## 1. Definition

- **Expected:** after a Kraken spot candle socket reconnects, every symbol it
  carried is subscribed again and keeps receiving candles. A subscribe Kraken
  refuses for rate is either dropped from the subscribed set (so the next
  `candlesRequests` re-subscribes it) or re-sent — never neither.
- **Actual:** the socket's symbols are re-sent as one message per earlier
  500 ms flush window, all in the same instant. Kraken answers the tail with
  `Exceeded msg rate`. Those refusals match nothing we track, so the symbols
  stay recorded as subscribed while receiving no candles.

## 2. Evidence

- Candle connector log: `00:13:10.138Z Kraken spot candle interval=60
  reconnected spotPublicV2`, then 32 ms later nine `Exceeded msg rate`
  subscribe exceptions with consecutive `req_id`s and **no** `rejected ohlc
  subscribe … retried` suffix (the suffix is printed only when the refusal is
  matched to a pending batch). The same shape recurs on other days.
- `@siebly/kraken-api` `subscribeTopicsForWsKey` stores each `subscribe()` call
  as its own topic (`wsStore.addTopic`, deduped only by deep equality, so each
  flush's different symbol list is a new topic); `onWsOpen` emits
  `reconnected` and then `onWsReadyForEvents` replays every stored topic in a
  tight loop (`requestSubscribeTopics`), one message per topic.
- `getSpotCandleClient`'s `settle()` returns `[]` when `pending` is empty, so
  the describe-error hook adds no suffix and drops nothing.
- Reproduced in `test/krakenSpotCandleReconnectReplay.test.ts` against the real
  client's store and replay: 12 flush windows → 12 messages at reconnect.

## 3. Requirements

- §3.1 A reconnect sends at most one subscribe message immediately, then the
  socket's full symbol set in `chunkSize` batches, one per flush window. The
  client's topic cache does not accumulate across reconnects.
- §3.2 A rate refusal of a replayed batch is attributed to that batch (dropped
  for re-request, existing behaviour).
- §3.3 A rate refusal that matches no pending batch re-queues the socket's
  unacked, not-in-flight symbols after a backoff; repeated refusals coalesce
  into one retry.

## 4. Assumption (root cause hypothesis)

The burst is the kraken-api client's own per-topic replay of the per-flush
subscribes added in 1.16.13. That change paced the *initial* subscribes but the
library replays its cache unpaced on reconnect, and those replayed messages are
not in `pending`, so their refusals are unattributable.
