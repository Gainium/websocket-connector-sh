# 016 — Bitget stream fees reach the platform as a cost, not a signed charge

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

§1.1 **Expected.** When a Bitget private-stream order update carries a fee,
the `ExecutionReport` this repo publishes states that fee as the **cost**
the venue charged — a positive amount in `feePaid` and in every
`feeBreakdown` leg — the same convention exchange-connector's REST Bitget
normalizer (`normalizeOrderFees`, "Magnitude, not sign") already uses for
the same order. main-app reads `feePaid`/`feeBreakdown` as a cost and
ignores anything `<= 0` as "not observed".

§1.2 **Actual.** Bitget reports a charge as a NEGATIVE number in
`feeDetail[].fee`. `prepareBitgetOrderMsg` (classic `orders` channel) and
`prepareBitgetUtaOrderMsg` (unified-account `order` topic) forward that
signed value unchanged. main-app's `streamFeeFields` assigns it onto the
order, after which `observedFeeSplit` returns `null` (fall back to the
estimate) and `observedFeeLegs` returns `[]` (the per-asset fee ledger never
sees the fee). A stream update arriving after the REST poll replaces a
usable REST fee with this unusable one.

§1.3 **Unchanged.** A non-negative Bitget fee is forwarded exactly as today
(byte-for-byte). No other venue's mapper changes: venues that report a
credit (e.g. Hyperliquid maker rebates) are not turned into costs. Which leg
is chosen for `feePaid`/`feeAsset` on a multi-leg fee is unchanged.

## §2 Evidence

§2.1 Code path: `src/userStream.ts` `prepareBitgetOrderMsg` →
`feeBreakdown: data.feeDetail.map(d => ({asset: d.feeCoin, amount: d.fee}))`,
`feePaid: primaryFeeLeg?.fee`. The existing test
`test/venueFeeForwarding.test.ts` pins `-0.05` as the forwarded value.

§2.2 main-app core `src/bot/orderFee.ts` `observedFeeSplit` and
`src/bot/feeLedger.ts` `observedFeeLegs` both skip `leg.amount <= 0`.

§2.3 Persisted state: stored Bitget orders carry a NEGATIVE `feePaid`
together with a one-leg `feeBreakdown` — spot (mostly BGB-paid) and USDT-M
alike. The REST normalizer never emits a negative fee and never emits
`feeBreakdown` for a single asset, so these values can only have been
written by the stream mapper: the path runs and its output is persisted.

## §3 Assumption (hypothesis)

The stream mapper is the only place the sign is lost: normalizing a
negative Bitget fee to its magnitude in both `feePaid` and `feeBreakdown`
makes main-app's existing fee processing book it — a USDT fee as
`{base: 0, quote: 0.05}`, a BGB fee as one ledger leg (and, being off-pair,
still a `null` split, as REST-sourced BGB fees already are).
