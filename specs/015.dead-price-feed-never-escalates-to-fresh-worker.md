# 015 — a price feed that stays dead is rebuilt in-thread forever

Bug spec (SKILL.md Part 0). Scope: `src/price/service.ts` (the worker's
uncaughtException escalation) and the liveness signal in `src/price/common.ts`.

## §1 Definition

### §1.1 Expected

**§1.1a** — a stall is first answered by the in-thread connector rebuild
(`service.ts` → `stream.stop()` + `getStream()`). That first-line reconnect is
kept for short interruptions.

**§1.1b** — when the same feed (exchange × price/candle) stalls
`STALL_EXIT_THRESHOLD` (3) times with no data between, the worker thread exits
with code 1 so `priceConnector.initWorker`'s `exit` handler starts a fresh
thread, about 2.5–3 minutes into the outage at the 50s watchdog cadence.

**§1.1c** — the first real tick or candle frame for that feed resets its count.
Stalls of other feeds do not count toward it, and data from other feeds does
not reset it.

**§1.1d** — the nightly 02:00 process exit (`index.price.ts`) is unchanged.

### §1.2 Actual

The escalation in `service.ts` cannot fire:

```ts
const retryCount = 1
...
if (retryStart + retryTimeout > time) {
  retry++                       // retry is already >= 1 here, so this makes it >= 2
  if (retry === retryCount) process.exit(1)   // 2 === 1 never holds
} else {
  retry = 1
}
```

The first error sets `retry = 1`, and every later error inside 60s increments
it past 1, so the worker never exits. The worker rebuilds the connector in the
same thread without end.

## §2 Evidence

- Production, 2026-09-24 06:27Z → 09-25 01:59Z: `Exchange exceed connect time
  50s | bitgetUsdm` repeated about once a minute for ~19.5h. There were roughly
  1,090 in-thread rebuilds and zero `Worker stopped` lines, and recovery came
  only at the 02:00 process start (triage, log-verified).
- Local repro (test/fixtures/stalledPriceWorker.ts): the real `service.ts` and
  `CommonConnector` watchdog in a real worker thread against a venue that never
  ticks gave 21 consecutive stall exceptions and 22 rebuilds in 8s, with no
  self-exit.
- `git blame`: `retryCount = 1` / `retry === retryCount` date from 38b5d4f
  (2025-06-26, initial release import). Latent.

## §3 Assumption

A fresh worker thread discards state that an in-thread rebuild keeps, such as
module-level `IdMutex` locks and sockets or timers of stopped connectors.
Recovery at a process start is consistent with that. This fix does not claim to
identify which piece of thread state held Bitget dead. It guarantees the
escalation that already recovered the feed once (a fresh start) happens within
minutes rather than at 02:00.

## §4 Out of scope

- The nightly restart.
- The in-thread first-line reconnect and the existing `retry` bookkeeping for
  non-stall errors.
- Per-connector targeted restarts (`handleStall`), which never throw and are
  therefore not counted.
