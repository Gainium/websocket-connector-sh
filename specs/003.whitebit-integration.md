# 003 — WhiteBit exchange integration (spot + USDⓈ-M perps) — streams

## §1. Context

Companion to `exchange-connector-sh` spec 002 (same integration, same
Step-0 feasibility verdict: spot + USDⓈ-M linear only, no Coin-M). This
repo's enum string values **must match spec 002 §2.1 exactly**
(`whitebit`, `whitebitUsdm`) — they are a cross-repo contract the moment
both PRs exist. Scoped to this repo only; `websocket-connector` (the
satellite that bumps this repo as `core/`) is a later PR.

## §2. Desired behaviour

### §2.1 Enum & paper twins (§2.1)

```ts
whitebit = 'whitebit'
whitebitUsdm = 'whitebitUsdm'
paperWhitebit = 'paperWhitebit'
paperWhitebitUsdm = 'paperWhitebitUsdm'
```

`mapPaperToReal`: `paperWhitebit → whitebit`, `paperWhitebitUsdm →
whitebitUsdm` — same shape as every existing pair in `utils/common.ts`.
Both paper ids also added to `userStream.ts`'s `paperExchanges` array and
`PaperExchangeType`.

### §2.2 Price/candle connector (§2.2)

WhiteBit has no npm SDK (confirmed, same finding as spec 002 §2.5) — build
`src/price/whitebit.ts` as a hand-rolled raw-`ws` client on the
**Hyperliquid pattern** (`src/utils/hyperliquidUserClient.ts`'s shape:
manual open/subscribe/reconnect + an app-level `setInterval` ping), not the
Kraken pattern (SDK-delegated connection lifecycle) — WhiteBit gives us no
SDK to delegate to.

- Single endpoint: `wss://wss.whitebit.com/ws`, JSON-RPC envelope
  (`{id, method, params}` requests; `{id, result, error}` responses;
  `{id: null, method, params}` on unsolicited server push). Public
  channels are unauthenticated — no `authorize` call needed for
  price/candle data (§2.5 covers the private/authorized side).
- **Ping confirmed, exact shape**: request
  `{"id": <n>, "method": "ping", "params": []}`, response
  `{"id": <n>, "result": "pong", "error": null}`. Docs state explicitly:
  send one every 50s; server times out idle connections at 60s. This is
  required client-side logic WhiteBit doesn't give us for free — unlike
  Kraken, where the SDK's own keepalive made this a non-issue (confirmed
  absent from `kraken.ts`).
- Candle subscribe: confirmed method `candles_subscribe`, params
  `[market, intervalSeconds]` (**interval is an integer in seconds**, e.g.
  `900` for 15m — not the string form (`'15m'`) WhiteBit's own REST kline
  endpoint uses, and not this repo's canonical interval enum either; a
  mapping table from Gainium's interval enum → WhiteBit's seconds value is
  required, §3.5). Server pushes `candles_update` with params
  `[time, open, close, high, low, volume_stock, volume_money, market]` —
  **same open/close-before-high/low column order as the REST kline
  endpoint** (spec 002 §2.3's gotcha, confirmed to also apply at the WS
  layer). Parse by explicit index.
- Trade subscribe: **confirmed**, method `trades_subscribe`, params = an
  array of market-name strings (`[]` subscribes to every market — almost
  certainly the wrong choice here, this repo subscribes per-symbol on
  demand like every other connector). Server pushes `trades_update` with
  params `[market, [{id, time, price, amount, type, rpi?}]]` — `type` is
  `"buy"`/`"sell"`, `time` is a float Unix timestamp (seconds, not ms —
  differs from the candle channel's integer-seconds `time` field, worth a
  deliberate unit conversion, not a copy-paste from the candle parser).
- Republish onto Redis using this repo's **exact, hard-contract** channel
  name templates (confirmed verbatim from `src/price/common.ts`, shared
  base class every connector including Kraken's already goes through — no
  new channel-naming code needed, just correct `symbol`/`exchange`/
  `interval` values passed into the existing `cbWs`/`cbWsTrade` calls):
  - `` `trade@${symbol}@${exchange}` ``
  - `` `${symbol}@${exchange}@${interval}Candle` `` (via
    `getCandleRoomName`)

### §2.4 Private user stream (§2.4)

`src/userStream.ts` gets a WhiteBit branch built on the **same hand-rolled
pattern as §2.2**, not Kraken's SDK-constructor pattern (no SDK exists to
hand credentials to). Concretely:

1. Open the same `wss://wss.whitebit.com/ws` endpoint.
2. **Confirmed — not a WS-side signature at all.** `authorize`'s params are
   `[token, "public"]`, where `token` comes from a separate authenticated
   REST call: `POST /api/v4/profile/websocket_token`. So the real flow is:
   REST-sign a request for a token (using the same HMAC-SHA512 scheme as
   spec 002 §2.5, one extra dependency on that repo's signing logic, or a
   duplicated minimal signer here — **decide which in the plan**), then
   `authorize` over WS with the returned token. No nonce/signature travels
   over the WS connection itself. Response:
   `{id, result: {status: "success"}, error: null}`.
   **New open item, §3.6**: the REST token's lifetime/refresh behavior
   (single-use? expires after N minutes? reusable across reconnects?)
   wasn't in the page excerpt read — matters for reconnect logic.
3. Await the correlated response by `id` (JSON-RPC request/response
   correlation is new plumbing this repo doesn't currently have anywhere
   — Kraken's SDK does this internally, Hyperliquid's user client doesn't
   need it because its private feed doesn't use a request/response
   handshake the same way). This correlation layer is the one genuinely
   new piece of infrastructure this integration adds to `userStream.ts`,
   not just "another exchange branch" — but it's now simpler than
   originally scoped, since `authorize` is the *only* request needing a
   correlated response; `ping` (§2.2) is fire-and-forget from this
   client's perspective (WhiteBit responds, but nothing here needs to
   await it), and channel `_subscribe` calls are not confirmed to ack
   individually the way `authorize` does.
4. On success, subscribe to the private channels — **three confirmed in
   detail**, rest confirmed to exist but not read past the channel-name
   level (§3.4 narrowed, not eliminated):
   - `balanceSpot_subscribe` (params: array of asset tickers, `[]` = all)
     → `balanceSpot_update`, pushed per-asset as
     `{ASSET: {available, freeze}}`, throttled to 1/sec while changing.
   - `ordersExecuted_subscribe` (params: `[markets[], filter]`, filter
     0=limit+market, 1=limit only, 2=market only) → `ordersExecuted_update`,
     order objects with `status` (`"FILLED"`, `"CANCELED"`, …), `side`
     (1=sell, 2=buy — **numeric, not a string**, different convention from
     this repo's other exchanges' string sides — map explicitly),
     `position_side` (LONG/SHORT/BOTH, usdm only), `deal_stock`/
     `deal_money`/`deal_fee`.
   - `positionsMargin_subscribe` (usdm only, params `[]`) →
     `positionsMargin_update`, **full snapshot** of every open position
     every second (not incremental deltas — the normalizer must diff
     against previously-seen position ids itself if downstream needs
     open/close *events* rather than periodic state).
   - Balance-margin, orders-pending, deals, margin-position-events, and
     borrows/borrows-events channels are confirmed to exist (named in the
     docs index) but their message shapes weren't read in this pass —
     lower priority, since `balanceSpot`+`ordersExecuted`+`positionsMargin`
     already cover the three `UserDataStreamEvent` cases this repo
     actually normalizes into; read the rest only if gate 5 finds a gap
     these three don't cover.
5. Start the same ~50s ping timer as §2.2.
6. Normalize each pushed message into the existing
   `UserDataStreamEvent` union (`executionReport` /
   `outboundAccountPosition` / `balanceUpdate`) so downstream Redis
   consumers (main-app, paper-trading) need zero new handling code — the
   mapping from WhiteBit's own field names to this shape happens entirely
   inside this repo's WhiteBit branch, matching how every other exchange
   in `userStream.ts` normalizes.

### §2.5 `getAllExchangeInfo` REST branch (§2.5)

WhiteBit does have a public REST all-markets endpoint (per exchange-
connector-sh's Market Info work, spec 002 §2.4) — follow the **Kraken
pattern** in `src/utils/exchange.ts` (a bespoke branch calling the
exchange's own REST client, excluded from the generic internal-proxy
branch), not the **Hyperliquid pattern** (no branch at all, relies
entirely on the generic proxy) — WhiteBit isn't in the situation
Hyperliquid is (no REST symbol list at all).
