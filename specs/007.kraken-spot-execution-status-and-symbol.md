# 007 — Kraken spot `executions`: read `order_status`, and carry the symbol onto the sparse terminal frames

Bug spec (SKILL.md Part 0). Kraken **spot** only (`ExchangeEnum.kraken`,
channel `executions`). Kraken **futures** (`fills` / `open_orders`) is a
different payload family and is out of scope.

## §1 Definition

### §1.1 Expected

`prepareKrakenOrderMsg` turns a Kraken WS v2 `executions` entry into an
`ExecutionReport`. For a spot order that fills, the emitted report must carry
`orderStatus: 'FILLED'` (and `'PARTIALLY_FILLED'` / `'CANCELED'` for the
corresponding venue states), so that `app-sh`'s
`convertExecutionReportToOrder` → `onFilled` books the fill from the stream,
in real time. Every emitted report must also carry the order's `symbol`.

### §1.2 Actual

Two independent defects on the same code path:

**(a) The status is read from a field the venue never sends.**
`src/userStream.ts:4618` reads `order.status`. Kraken WS v2's `executions`
channel names that field **`order_status`**. `order.status` is therefore
`undefined` for every spot execution, `mapKrakenOrderStatus(undefined)` hits
its `if (!status) return 'NEW'` guard (`:4768`), and **100% of Kraken spot
executions are emitted as `NEW`** — including the ones that say the order
filled.

`NEW` is a no-op for fills in `app-sh`
(`core/src/bot/main.ts:5995-5996` — only `FILLED` calls `onFilled`, only
`PARTIALLY_FILLED` calls `onPartiallyFilled`), so the fill is never booked
from the stream. It is eventually recovered by the fill-failsafe REST sweep
(`main-app/src/fillFailsafe/`), which is what makes the user-visible symptom a
**delay** rather than a permanently lost fill.

**(b) The terminal frames carry no `symbol`.**
Kraken sends the order's `symbol` only on the *detail* frames
(`pending_new`, `trade`, and the `executions` snapshot). The *summary* frames
that announce the terminal state — `exec_type` `filled` / `canceled` /
`amended` — carry ids and totals only. `symbol` therefore resolves to `''`
(`:4570-4571`) on exactly the frames that matter most.

This does not break routing — `app-sh` routes by `clientOrderId`, not symbol
(`core/src/bot/sharedStream.ts:78-93`) — but it does break pricing:
`convertExecutionReportToOrder` does `const ed = await
this.getExchangeInfo(msg.symbol)` and then
`this.math.round(quote / base, ed?.priceAssetPrecision)`
(`core/src/bot/main.ts:5181,5190`). With `symbol: ''` the lookup misses,
`priceAssetPrecision` is `undefined`, and `MathHelper.round`'s
`precision = 2` default (`core/src/utils/math.ts:27`) silently rounds the
booked fill price **to 2 decimals**. Harmless on `SOL/USDC`; destructive on a
sub-cent pair (`0.0123 → 0.01`).

Defect (b) is latent today — nothing acts on these reports while (a) forces
them all to `NEW`. Fixing (a) alone would activate it.

## §2 Evidence

Read-only prod capture, 2000 parsed `krakenexecutions` payloads from the live
+ archived user-stream logs (the connector logs each emitted report's
`uniqueMessageId`, which embeds the raw venue entry — `:3893`):

| Measurement | Result |
|---|---|
| payloads carrying `status` | **0 / 2000** |
| payloads carrying `order_status` | **2000 / 2000** |
| terminal (`filled`/`canceled`) frames carrying `symbol` | **0 / 191** |
| `symbol` present by `exec_type` | `trade` 247/247, `pending_new` 232/232, `new` 1097/1329, `filled` **0/96**, `canceled` **0/95** |

Real captured lifecycle for one grid order (`SOL/USDC`, verbatim, in arrival
order — note `order_status` present throughout, `symbol` only on the last two):

```
21:32:36.031  {"order_status":"new","exec_type":"new","cl_ord_id":"GRID-BO-…","order_id":"OJUFYI-…"}
21:32:36.033  {"order_status":"filled","exec_type":"filled","cum_qty":1.80406743,"cum_cost":180.31654,"avg_price":99.95,…}
21:32:36.037  {"order_id":"OJUFYI-…","exec_type":"trade","symbol":"SOL/USDC","order_status":"partially_filled",…}
21:32:36.052  {"order_id":"OJUFYI-…","symbol":"SOL/USDC","exec_type":"pending_new","order_status":"pending_new",…}
```

The repo's own existing fixture already encodes the correct field name —
`test/venueFeeForwarding.test.ts:286,339` is Kraken's published v2 example,
verbatim, and uses `order_status`. That test asserts only fee fields, which is
why it never caught (a).

**Frame ordering** (what a symbol cache can and cannot resolve): the normal
sequence is `… → trade → filled`. Of 96 orders carrying both, **90** put
`trade` (symbol-bearing) before `filled`; **6** are market orders whose burst
is inverted (`filled` before `trade`). Across all 191 terminal frames, **145
(75.9%)** already had a symbol-bearing frame for the same order earlier in the
capture; of the 46 that did not, 40 are cancels of orders placed before the
capture window opened (an artefact of the window, not of the venue).

## §3 Assumption

Root-cause hypothesis, stated as hypothesis:

1. **(a)** is a plain field-name error: the spot branch was written against
   the REST/v1 vocabulary (`status`; the `mapKrakenOrderStatus` comment at
   `:4772` lists `pending, open, closed, …`, which is the REST order-status
   set) while the v2 `executions` channel it actually consumes sends
   `order_status` with the values `pending_new, new, partially_filled,
   filled, canceled`. `mapKrakenOrderStatus` already maps all of those
   correctly — it is only ever handed `undefined`.
2. **(b)** is a shape assumption: the branch assumes every `executions` entry
   is self-describing. The terminal summary frames are deltas against an
   order the venue has already described, so the symbol must be carried
   forward per `order_id` from an earlier frame.

Gate 2's tests must fail *because of these two things* — i.e. a report built
from a real `trade`/`filled` payload comes back `NEW`, and a report built
from a real `filled` payload comes back with `symbol: ''` — not for any
incidental reason.

## §4 Scope / non-goals

- §4.1 Kraken **futures** (`fills`, `open_orders`) is untouched. Its cancel
  branch also emits `symbol: ''` (`:4702`), by a different mechanism, and is
  not on this causal path.
- §4.2 The 6/151 inverted market-order bursts (§2) are **not** solved by a
  cache alone — when `filled` genuinely precedes every symbol-bearing frame
  there is nothing yet to read. Those keep today's `symbol: ''`; this is
  unchanged behaviour, not a regression. Mitigated in part by resolving
  within a frame before mapping it (§5.3), which covers the batched case.
- §4.3 No change to `ExecutionReport`'s shape, to any Redis channel, or to
  `mapKrakenOrderStatus`'s mapping table — only to what is fed into it.
- §4.4 Observed while testing, deliberately left alone: this branch passes
  Kraken's **numeric** `cum_qty`/`cum_cost` straight into
  `totalTradeQuantity`/`totalQuoteTradeQuantity`, which `ExecutionReport`
  types as `string`. Pre-existing on every Kraken spot frame and benign —
  `app-sh` persists through mongoose `RequiredString` (which casts) and
  coerces every read with `+`/`parseFloat`. Normalizing it would change the
  quantity values spec 003's tests pin, so it is out of scope here.

## §5 Required behaviour

- §5.1 A spot execution entry whose `order_status` is `filled` emits
  `orderStatus: 'FILLED'`; `partially_filled` → `'PARTIALLY_FILLED'`;
  `canceled` → `'CANCELED'`; `new`/`pending_new` → `'NEW'`.
- §5.2 An entry that carries no `symbol` emits the symbol most recently seen
  for the same `order_id` (normalized through `wsnameToNormalized` exactly as
  a first-hand symbol is), falling back to `''` when nothing is known.
- §5.3 Symbols are learned from every entry in a frame *before* any entry in
  that frame is mapped, so a batched frame that carries the detail and the
  summary together resolves regardless of their order within the batch.
- §5.4 An entry that does carry a `symbol` is unaffected — same normalization,
  same output as today.
- §5.5 The fee accumulation, `fee_usd_equiv` pass-through and cumulative
  quantity behaviour pinned by spec 003 stay byte-for-byte unchanged.
