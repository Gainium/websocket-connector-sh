# 008 — Binance spot WS-API user data stream is not resubscribed after a reconnect

Bug spec. Binance **spot** with Ed25519 keys only — the `WebsocketAPIClient` path in
`userStream.ts` (`useWebsocketAPI`). binanceUS, binanceUsdm and binanceCoinm use the plain
`WebsocketClient` and are out of scope (§4.2).

## 1. Definition

### 1.1 Expected

- §1.1.1 When the WS-API connection drops and the SDK reconnects it, the account's user data
  stream is subscribed again, and order/balance events keep arriving without rebuilding the room.
- §1.1.2 The account's bots are told to reconcile (`Subscribed to user <id>` on
  `userStreamInfo<id>`) once the stream is subscribed again, so the REST reconcile covers
  everything up to the moment events resume.
- §1.1.3 A room torn down while a resubscribe is queued sends nothing more to Binance.

### 1.2 Actual

After a transport reconnect the connector logs `ws has reconnected mainWSAPI`, the session logs
back on, and no user-stream event for that account ever arrives again. REST keeps working, so bots
keep placing orders, but fills and cancels are only discovered by reconcile paths outside the
stream; a grid whose resting orders filled unseen stops replacing them. The account recovers only
when its stream is rebuilt (a room restart, or the connector process restarting).

Reported externally on a self-hosted install, reproduced on two separate days; an account-level
stream restart restored events immediately each time, with no data changes.

## 2. Evidence

### 2.1 Vendor SDK (`binance@3.6.3`)

A WS-API user data stream is bound to its connection; a new connection carries no subscription.
The SDK handles that itself:

- `WebsocketAPIClient` constructor → `setupRequiredEventListeners()`
  (`lib/websocket-api-client.js:726`) attaches `wsClient.on('reconnected', …)` →
  `handleWSReconnectedEvent()`.
- `handleWSReconnectedEvent()` (`:840`) checks `subscribedUserDataStreamState[wsKey]` and queues
  `tryResubscribeUserDataStream()` after `resubscribeUserDataStreamDelaySeconds` (default 2), which
  calls `subscribeUserDataStream()` again.
- The same constructor's `setupOptionalEventListeners()` attaches console-logging listeners on
  `open` / `reconnecting` / `reconnected` / `authenticated` / `exception`, switchable with
  `attachEventListeners: false`.

### 2.2 Connector

Right after building the client, `userStream.ts` called
`client.removeAllListeners('open' | 'reconnecting' | 'reconnected' | 'authenticated' | 'exception')`
on it. On the WS-API client that removed the SDK's required `reconnected` listener along with the
logging ones, so `handleWSReconnectedEvent()` never ran.

These calls predate the WS-API path: on the plain `WebsocketClient` the SDK attaches no listeners,
so they were no-ops. They became harmful when the Ed25519 WS-API client was introduced.

## 3. Assumption (hypothesis, not fact)

Stripping `reconnected` listeners from the WS-API client is sufficient to lose the resubscribe.
Test `§3 baseline` in `test/binanceWsApiResubscribe.test.ts` drives the real SDK client: with
the listeners stripped a reconnect sends no `userDataStream.subscribe`; without stripping it
sends one.

## 4. Scope

### 4.1 In scope

- §4.1.1 Build the WS-API client with `attachEventListeners: false` instead of stripping
  listeners; remove the `removeAllListeners` calls for all Binance user-stream clients (each client
  is brand new, so they can only ever remove SDK listeners).
- §4.1.2 On the WS-API path, publish the reconcile signal after the SDK's resubscribe is accepted
  (§1.1.2) instead of on `reconnected`, which lands ~2s before the stream is back.
- §4.1.3 `stopMethod` turns a queued SDK resubscribe into a no-op (§1.1.3); sending it would
  re-open the connection the room just closed.

Implementation: `src/binance-custom/wsApiUserStream.ts`.

### 4.2 Out of scope

- §4.2.1 binanceUS / binanceUsdm / binanceCoinm (listenKey streams on `WebsocketClient`). Their
  `reconnected` handler keeps publishing the reconcile signal as before.
- §4.2.2 A liveness check that verifies the venue subscription independently of the transport.

### 4.3 Invariants that must not move

- §4.3.1 The connector's own `message` / `open` / `reconnecting` / `reconnected` / `close` /
  `exception` handlers behave as before, including the auth-reject circuit-breaker and
  `noteReconnect()` flap counting.
- §4.3.2 The initial subscribe does not publish an extra reconcile signal.
- §4.3.3 Lossless order-id parsing (spec 004) still applies to the WS-API client.
