## Contract decisions

- Hand-rolled client on the Hyperliquid pattern, not an SDK wrapper (no
  SDK exists) — same call as spec 002 §2.5 made for the REST side.
- One connector class handles both `whitebit`/`whitebitUsdm`, symbol
  suffix differentiates them (spec §2.2) — avoids duplicating the
  connection/ping/reconnect plumbing across two near-identical classes.
- The JSON-RPC request/response correlation helper (Build order step 6)
  is written as a small reusable piece inside the WhiteBit branch, not
  promoted to a shared cross-exchange utility in this PR — no second
  exchange needs it yet, and premature sharing here would be guessing at
  a shape before a second consumer exists to validate it against.

## Blast radius

1. **Other call sites.** `ExchangeEnum`/`mapPaperToReal` in
   `utils/common.ts` are read by every existing connector and by
   `userStream.ts`'s `paperExchanges` array — grepped, all sites needing a
   WhiteBit entry are listed in Build order steps 3–6; no other file
   pattern-matches on a hardcoded exchange list in this repo.
2. **`core/` submodule.** This repo *is* the `core/` submodule for
   `websocket-connector` — this PR's streams are inert until that repo
   bumps its pointer, out of scope here (spec §4). No existing exchange's
   behavior changes.
3. **Cross-repo contract (the one that matters most here).** The Redis
   channel strings this PR publishes to
   (`trade@{symbol}@{exchange}`, `{symbol}@{exchange}@{interval}Candle`)
   and the `UserDataStreamEvent` shape are read by `app-sh` and
   `paper-trading-sh` — neither is touched by this PR, but both are
   *implicitly* extended the moment WhiteBit data starts flowing once this
   is deployed and `whitebit`/`whitebitUsdm` accounts exist. This PR alone
   is safe (no existing consumer reads a WhiteBit-tagged message today);
   the risk surfaces only once a later `app-sh` PR (out of scope, per the
   runbook's PR ordering — that's `app-sh`'s own spec) starts creating
   WhiteBit accounts.
4. **Other tests exercising this path.** `krakenSpotBalances.test.ts` and
   `krakenFillCumulative.test.ts` must stay green — nothing in this plan
   touches Kraken's code paths, only adds new WhiteBit-specific files and
   enum members.
