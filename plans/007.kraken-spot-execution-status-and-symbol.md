# 007 — Plan: Kraken spot `executions` status + symbol

Implements [`specs/007.kraken-spot-execution-status-and-symbol.md`](../specs/007.kraken-spot-execution-status-and-symbol.md).

## Solution

All changes are inside the spot `executions` branch of
`prepareKrakenOrderMsg` (`src/userStream.ts:4568-4635`) plus one
module-scope map declaration.

1. **§5.1 — read the right field.** `this.mapKrakenOrderStatus(order.status)`
   → `this.mapKrakenOrderStatus(order.order_status ?? order.status)`.
   `mapKrakenOrderStatus`'s mapping table already handles every v2 value
   (`new`, `partially_filled`, `filled`, `canceled`; `pending_new` falls
   through its trailing `return 'NEW'`, which is the correct answer) — it was
   only ever being handed `undefined`. Keeping `?? order.status` as a
   fallback costs nothing and keeps any hypothetical v1-shaped payload
   working. Its stale comment block, which lists the REST vocabulary
   (`pending, open, closed`) rather than the v2 one this branch consumes, is
   corrected in place — that comment is what made the wrong field look right.

2. **§5.2/§5.3 — carry the symbol forward per order id.** A module-scope
   `ExpirableMap<string, string>` (`krakenSpotOrderSymbols`) keyed by
   `order_id || cl_ord_id`, holding the **normalized** symbol. Populated from
   every entry that carries a `symbol`; read by every entry that does not.
   The frame's entries are walked once to learn symbols *before* the
   `.map()` that builds the reports, so a batched frame is order-independent
   within itself (§5.3).

### Tier (Part 4 / runbook)

**Tier 0 — no extraction.** The change is two expressions and one lookup
table inside a branch that is already a self-contained `.map()` over one
venue's payload; there is no decision-logic-tangled-with-I/O block on the
causal path to pull out. The surrounding method is pure over its inputs
already (its only I/O, `getKrakenMaps`, is awaited once at the top and is
what the sibling tests stub). Extracting a module here would create a new
shape for no testability gain — the existing tests already drive
`prepareKrakenOrderMsg` directly. Not Tier 1 for that reason; not Tier 2/3
because nothing on this path is being re-architected.

### Reuse (no new utility)

`ExpirableMap` (`src/utils/expirableMap.ts`) is the established idiom for
exactly this — per-order state keyed by exchange order id, self-evicting so
an order whose last frame never arrives cannot leak. Two direct neighbours in
this same file already do it: `krakenFillTotals` (`:622`) and
`krakenSpotFeeTotals` (`:635`). The new map mirrors their declaration shape,
placement and comment style. No new helper is introduced; symbol
normalization keeps using the existing `maps.wsnameToNormalized`.

### TTL

24h (`KRAKEN_SPOT_SYMBOL_TTL_MS`-overridable), vs. the 1h the two neighbouring
maps use. Those accumulate *fill/fee totals*, which are only meaningful while
an order is actively filling; this one must survive an order **resting**. The
`filled` case would tolerate 1h — its `trade` frame arrives in the same burst
and repopulates the map — but a GTC grid order cancelled hours after
placement has no such frame, and cancels are 95 of the 191 terminal frames in
§2's capture. Entries are one short string; the map self-evicts per entry.

## Blast radius

1. **Other call sites.** `prepareKrakenOrderMsg` has exactly one caller,
   `client.on('message')` at `:3346`, reached only for
   `ExchangeEnum.kraken` / `krakenUsdm`. The edited branch is gated on
   `channel === 'executions'`, which only Kraken **spot** subscribes to
   (futures uses `fills`/`open_orders`, `:3324`). `mapKrakenOrderStatus` has
   one other caller — none; it is called only from `:4618`. Verified by grep.
2. **`core/` submodule.** Yes — this file is in `websocket-connector-sh`,
   shared with the self-hosted platform and both prod checkouts. The parent's
   pointer must be bumped at ship time. No exported signature changes, so
   consuming services need no coordinated change.
3. **Cross-service contracts (root CLAUDE.md Danger List).** `ExecutionReport`
   is published to Redis on the per-`exchangeUUID` channel and consumed by
   `app-sh`. **No field is added, removed or renamed** — two existing fields
   (`orderStatus`, `symbol`) start carrying correct values on Kraken spot
   where they previously carried `'NEW'` and `''`. That is the fix, and it is
   confined to one venue. Contract shape untouched (spec §4.3).
   - *Behavioural* blast radius worth naming: Kraken spot fills begin booking
     from the stream instead of ~15 min later via the fill-failsafe REST
     sweep. That is the intended effect, and the failsafe remains as the
     backstop it already is.
4. **Other tests on this path.** `test/venueFeeForwarding.test.ts` drives the
   same branch (Kraken fee accumulation, spec 003) and
   `test/krakenFillCumulative.test.ts` drives the futures `fills` branch of
   the same method. Both must stay green; §5.5 duplicates the fee assertion
   inside the new test as a tripwire.

## Gate 4 — plan vs spec

Walked §5.1–§5.5: each has a row above. Every decision made here
(`?? order.status` fallback, TTL length, map placement, Tier 0) was left open
by the spec rather than contradicting it. The Solution fixes the two causes
named in §3 — the field name and the carry-forward of symbol — not a
downstream symptom: notably it does **not** paper over the 2-decimal price
rounding in `app-sh`, which is correct behaviour given a correct symbol and
is left alone. §4.2's residual (inverted market-order bursts across separate
frames) is accepted and documented, not silently closed.
