# 003 — Plan: forward the venue's fee on every exchange

Spec: `specs/003.forward-venue-fee-for-all-exchanges.md`.

## Solution

Add four optional fields to `ExecutionReport` (`src/userStream.ts:259-277`):
`feePaid?: string`, `feeAsset?: string`, `feeBreakdown?: { asset: string;
amount: string }[]`, `feePaidUsd?: string`. (`feeSide` is not added here —
no venue in scope names a side rather than a ticker; `app-sh`'s
`observedFeeSplit` already accepts either, so it stays available if a
future venue needs it.)

Per venue, in each `prepare*OrderMsg()`, add the object-literal fields the
tests in `test/venueFeeForwarding.test.ts` pin:

| Venue | Add to the returned object |
|---|---|
| Bybit | `feePaid: data.cumExecFee, feeAsset: data.feeCurrency` |
| OKX | `feePaid: data.fee, feeAsset: data.feeCcy` — **not** `fillFee`/`fillFeeCcy` |
| Bitget | `feeBreakdown: data.feeDetail.map(d => ({ asset: d.feeCoin, amount: d.fee }))` — **not** the singular `fillFee` |
| Coinbase | `feePaid: order.total_fees` (no `feeAsset` — §4) |
| Hyperliquid | accumulate `fee`/`feeToken` across `fills` the same way `filledSize`/`quote` already are in `buildHyperliquidExecutionReport` (`:4143-4150`), emit `feePaid`/`feeAsset` from the sum |
| Kraken (spot) | `feePaidUsd: data.fee_usd_equiv` (direct passthrough — documented as an order-level running total, §2.1); `feePaid`/`feeAsset` accumulated across `data.fees[]` per order via new `krakenSpotFeeTotals` state (treated as per-fill, conservatively, per spec §2.1, until §3.1's live capture says otherwise) |
| Kraken (futures) | **not implemented in this pass** — blocked on §3.1a, separate channel |

### Order of work

1. **§3 evidence first.** Before touching Bybit/OKX/Bitget code, capture one
   real private-order-update message per venue from prod logs (the
   mechanism `test/coinbasePartialFill.test.ts` and
   `test/krakenFillCumulative.test.ts` both document using) and confirm the
   fee field really is the order-level running total, not a per-fill
   delta. If a venue turns out to be per-fill, it moves to the Hyperliquid
   accumulation pattern instead of straight passthrough — a plan
   correction, not a spec disagreement, since the spec's §2.1 already
   names this fork and defers the answer to evidence.
2. Bybit, OKX, Coinbase — straight passthrough once §3 confirms cumulative
   (lowest risk, no new state).
3. Bitget — passthrough of `feeDetail` (already multi-leg/cumulative by
   its own model, per §2.1 — still worth a real payload check in step 1
   since Bitget's `fillFee` naming pattern is the one most likely to also
   apply to `feeDetail`).
4. Hyperliquid — add per-order fee accumulation. Reuse the shape of
   `krakenFillTotals` (`:602-605`, `ExpirableMap` keyed per order, deduped
   by trade id) rather than inventing a second mechanism — same problem
   (per-fill deltas need summing into a running total keyed by order),
   same lifecycle (expire with the order). A new `hyperliquidFeeTotals`
   map, deduped by `hl.Fill`'s trade id the same way `krakenFillTotals`
   dedupes by `fill_id` (`:4501-4512`).
5. Kraken (spot) — implement now, on the evidence already in hand
   (Kraken's own v2 docs, stronger than §3.2's field-name inference), with
   two conservative choices standing in for what a live payload would
   otherwise confirm: `fees[]` accumulated as per-fill (§2.1 — safe
   direction is under- not over-forwarding) and `feePaidUsd` passed
   through unaccumulated (documented as already a running total).
   `krakenSpotFeeTotals` mirrors the Hyperliquid map below — new
   `ExpirableMap`, keyed per order, summed by asset from `data.fees[]` on
   each `trade`/`filled` `exec_type` event, deduped the same way
   `krakenFillTotals` dedupes Kraken futures fills, keyed on `exec_id`
   (the `executions` channel's own per-trade identifier — the closest
   analogue to futures' `fill_id`). Still capture a real payload before
   this reaches prod, per §3.1's open items 2-3 (does this account's
   subscription actually receive these fields at all) — this is
   "implement against strong documented evidence," not "evidence
   satisfied."
6. Kraken (futures) — separate follow-up spec once research exists. Not
   attempted here.

## Contract decisions the spec left open

- **Coinbase `feeAsset`.** Leave unset. `app-sh/orderFee.ts:observedFeeSplit`
  already falls back safely (returns `null`, never books zero) when a fee
  has no resolvable currency, so an unset `feeAsset` is a safe "we don't
  know" rather than a guess that could silently mis-book a fee to the
  wrong side if Coinbase's fee-in-quote convention ever changes. Revisit
  only if `app-sh` needs the number sooner than a currency-safe design
  allows.
- **Hyperliquid accumulation state** — new `hyperliquidFeeTotals`
  (`ExpirableMap`), not folded into `krakenFillTotals` itself. Different
  venues, different message shapes; sharing the map would couple two
  unrelated exchanges' cleanup lifecycles for no benefit.
- **Kraken spot `fees[]` treated as per-fill, not cumulative.** §2.1/§3.1:
  the docs don't say either way; per-fill is the conservative default
  (under-forwarding a total is a smaller bug than over-forwarding one),
  and it's cheap to flip to straight passthrough once a live payload
  confirms cumulative — the accumulator just stops being needed, it
  doesn't need removing (an `ExpirableMap` summing a total that's already
  cumulative just re-sums to the same number... **no** — this is wrong if
  the field turns out to be genuinely cumulative: summing an
  already-cumulative number across events would inflate it. Flag this
  explicitly rather than gloss over it: if §3.1's live capture shows
  `fees[]` is cumulative, the fix is to stop accumulating and pass
  through directly, mirroring `feePaidUsd` — not a compatible no-op.
  Ship behind the same new-deal flag (`app-sh` spec `006` §3) precisely
  so this is cheap to correct before it's ever booked against real money.

## JIT extraction tier

**Tier 0/1 — no extraction.** Every change is an additive field on an
existing object-literal-returning normalizer (Tier-0-shaped: the smell
this repo already tolerates in every `prepare*OrderMsg()` is "one function,
one venue's raw-to-normalized mapping," and that shape is not being made
worse by adding three more field assignments). Hyperliquid's and Kraken
spot's new accumulation maps are new state next to `krakenFillTotals`,
matching that existing precedent's own shape — not a pure module, because
the accumulation is inseparable from the `ExpirableMap`/dedup-by-trade-id
I/O it already leans on for Kraken futures. Not Tier 2: there is no
free-standing calculation here worth a pure function on its own — it is
three lines of object construction per venue, not a decision.

## Blast radius

1. **Other call sites.** Each `prepare*OrderMsg()` is called from exactly
   one place — its own venue's WS message handler inside `setupWebsocket*`
   — confirmed by `grep` for each method name; no shared caller to break.
2. **`core/` submodule.** This repo **is** the `core/` submodule content
   (embedded in `websocket-connector` as `core/`, and in the prod
   `binance-websocket` checkout — confirmed via
   `websocket-connector/.gitmodules` and its own `CLAUDE.md`). Every
   change here is platform-wide once the submodule pointer in
   `websocket-connector` is bumped, same as any other change to this repo.
3. **Cross-service contract.** `ExecutionReport` is the informal
   JSON-over-Redis-pubsub contract to `app-sh` (no shared types package —
   confirmed, `app-sh` declares its own independent `CommonOrder`/`Order`
   types). Adding optional fields is additive and cannot break an existing
   consumer that doesn't read them yet — `app-sh`'s `orderFee.ts` is
   already written to treat every one of these fields as optional
   (`observedFeeSplit` returns `null` on absence). No existing field is
   renamed or removed. `websocket-connector/README.md` and
   `DEVELOPER_GUIDE.md`'s documented `ExecutionReport` shape is already
   stale against the real interface (field-name mismatches predate this
   change) — not fixed here, out of scope, flagged so it isn't mistaken
   for new drift this change caused.
4. **Restarting live streams.** Shipping this restarts every user-stream
   connection process. The change is inert for `app-sh` until `app-sh`
   spec `006` ships and is deployed to bot workers (per that spec's own
   blast radius) — publishing the field first, with nothing reading it
   yet, is the same staged-rollout shape the Aug 2026 Binance fee fix
   already used successfully (connector live, consumer dormant until a
   worker restart).
