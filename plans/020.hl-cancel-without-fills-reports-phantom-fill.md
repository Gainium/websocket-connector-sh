# 020 — plan: read a shrunk Hyperliquid cancel's fills from the venue

Spec: `specs/020.hl-cancel-without-fills-reports-phantom-fill.md`.

## Build order

1. Red: `test/hyperliquidCancelFillHistory.test.ts` drives the real
   `prepareHyperliquidOrder` with the production cancel frame and a stubbed
   `hlFetchFillsPage`, plus the pager on its own.
2. `utils/hyperliquidFillPark.ts`: `fetchHyperliquidOrderFills` — pages
   `userFillsByTime` forward, de-dupes by `tid`, filters by `oid`, throws past
   the page cap.
3. `userStream.ts`:
   - `hlInfo` (`hl.InfoClient`, 5s timeout, `HL_FILL_HISTORY_TIMEOUT_MS`);
   - `hlFetchFillsPage` / `hlOrderFillHistory` (null + `logger.warn` on failure);
   - `prepareHyperliquidOrder` calls it only for a non-filled terminal update
     with `origSz − sz > 0` and nothing buffered;
   - `buildHyperliquidExecutionReport(order, fills, fromHistory)` — with
     `fromHistory` and no fills, executed and quote are 0.

4. §4.3 revision (1.16.17): a failed lookup no longer emits `origSz − sz`
   inline. `hlRetryOrderFillHistory` retries it with doubling backoff, emits
   the first history-based report, and falls back to `origSz − sz` with an
   error log only after every attempt fails. `hlHistoryDeferred` keeps a
   replayed cancel from starting a second retry. Not routed through
   `hlFillParkResolver`: that ladder is keyed on FILLED updates and resolves
   to a REST `CommonOrder`/limitPx, neither of which applies to a cancel —
   only its retry-with-backoff shape is reused.

## Contract decisions

- The execution-report shape is unchanged. Only the quantity/quote/fee values
  of a shrunk cancel change, and only when the venue's history says so.
- No credentials: `userFillsByTime` is a public info call keyed by the account
  address the stream already subscribes with.

## Blast Radius

- Hyperliquid spot and perps user streams only; every other venue untouched.
  `filled`/`open` updates and the park → REST → limitPx ladder are unchanged.
- Callers of `buildHyperliquidExecutionReport`: `prepareHyperliquidOrder` and the
  park resolver's `buildEvent` — the new arg defaults to `false` for both.
- Cost: one info request (weight 20) per shrunk cancel, a rare event; it delays
  the rest of that `orderUpdates` batch by at most the timeout. On a 429 or
  timeout that order's report is deferred (up to ≈ 30s + the timeouts) while
  the lookup is retried; the old report is emitted only if every retry fails.
- Downstream (main-app) books less executed quantity on these cancels — the
  intended effect. Existing rows are not touched.
- Tests that stay green: `hyperliquidFillPark.test.ts`, `venueFeeForwarding.test.ts`.
