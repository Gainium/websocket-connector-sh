# 022 — plan

## Solution

In `getSpotCandleClient` (src/price/kraken.ts) add a `reconnected` listener
for `spotPublicV2`. It runs synchronously inside `onWsOpen`, before
`onWsReadyForEvents` reads the topic store, so it:

1. clears the client's stored topics (`getWsStore().getTopics(wsKey).clear()`),
   so the library replays nothing;
2. clears `pending` (in-flight batches died with the connection) and `acked`;
3. re-queues every `wsnames` entry and calls `scheduleCandleFlush` — the same
   paced path initial subscribes use, so each batch is tracked in `pending`.

`wsnames` becomes `Map<wsname, CandleSub>` (it needs the room to re-queue).
An `acked` set records successful acks. A new `scheduleCandleRetry` handles an
`Exceeded msg rate` that `settle()` cannot attribute: after 5 s it re-queues
symbols not acked and not queued/pending; one timer per socket coalesces bursts.
Retry timers are cleared in `stop()` and `restartKrakenCandleStreams`.

JIT tier: 0/1 — the change stays inside the existing per-socket closure; no
extraction (the logic is a few lines and already tested via the fake-`this`
harness).

## Blast Radius

1. Call sites: `wsnames` used only in `connectKrakenCandleStream` (`.has`,
   now `.set`) and the describe-error hook (`.delete`) — both work on a Map.
   `scheduleCandleFlush` unchanged.
2. File is under `core/` (websocket-connector-sh) — shared by the candle and
   price stream processes. Only spot candle sockets register the listener;
   ticker and futures sockets unchanged.
3. No Redis channel, payload or RabbitMQ contract touched.
4. `test/krakenSpotCandleSubscribeBatch.test.ts` exercises the same path and
   stays green; full core suite green.
