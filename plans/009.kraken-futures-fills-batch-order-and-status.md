# Plan 009 — Kraken futures `fills`: chronological batch order + cumulative-derived status

Implements `specs/009.kraken-futures-fills-batch-order-and-status.md`.

## 1. Contract decisions the spec left open

### 1.1 The sort key, and what happens when it is absent

Spec §4.1 says "by `time`, then `seq`". Concretely: `time` ascending, `seq`
ascending as tiebreak, **missing values compare equal**. `Array.prototype.sort`
is stable in V8, so a batch where neither field is present is mapped in
delivery order — byte-identical to today's behaviour. That is deliberate: the
fallback for "Kraken told us nothing about ordering" must be *the status quo*,
not a guess.

`seq` is the tiebreak rather than the primary key because it is a
per-connection counter and resets across reconnects; `time` does not.

### 1.2 How the status is derived — reuse, don't re-derive

Spec §4.2 asks for status from the cumulative rather than from one fill's
`remaining_order_qty`. **`src/utils/krakenOpenOrders.ts` already exports
exactly that arithmetic** — `krakenOpenOrderFill({qty: remaining, filled:
cumulative})` returns `{status, total: filled + remaining, filled, remaining}`,
i.e. "given how much is still open and how much has cumulatively executed, what
is the status and what was the original size?". It was written for the
`open_orders` feed in 2026-08-22, but the arithmetic is feed-agnostic; the only
reason the `fills` branch does not already use it is that it predates it.

**Decision: call the existing helper, add no new one.** Two things fall out of
it for free:

- `total` (= cumulative + remaining) becomes the emitted `quantity`. Once the
  batch is ordered this is the true original size on *every* report (§1.1c),
  replacing the ad-hoc `totals.qty + remaining` that drifted to 0.1506.
- `status` stops being a strict `fill.remaining_order_qty === 0` identity
  check. A fill that omits `remaining_order_qty` currently fails that check
  (`undefined !== 0`) and reports PARTIALLY_FILLED at the full quantity — an
  order that never terminates. Through the helper it is coerced to `0` and
  reports FILLED.

Rejected alternative: a monotonic `size = max(size, cumulative + remaining)`
tracked on the accumulator. Under the cross-**message** split of §5.3 the max
is fed a non-chronological cumulative and ratchets *above* the true size
(0.1094 for an order of 0.0955), after which `cumulative >= size` can never be
true and the order is **stuck PARTIALLY_FILLED forever** — a permanently open
deal, strictly worse than the bug being fixed. Given a correctly ordered batch
`cumulative >= size` and `remaining === 0` are algebraically the same
statement, so the max buys nothing on the path that actually broke.

Consequence of the above: spec §4.3's float tolerance is **not needed** and is
not implemented — there is no `>=` between two independently-accumulated
floats left to compare. Noted here because it is a spec section deliberately
not built.

### 1.3 `status: 'NEW'`

`krakenOpenOrderFill` returns `'NEW'` when the cumulative is 0 — reachable on
the `fills` feed only for a fill carrying no `qty`. `'NEW'` is a no-op for
fills in `app-sh`, i.e. a zero-quantity fill books nothing instead of booking
a phantom FILLED. Accepted as an improvement, not worked around.

## 2. Build order

1. `src/userStream.ts` — module-level pure comparator/orderer next to the
   `krakenFillTotals` declaration it serves (Tier 1 per the JIT runbook: named
   and documented, left in the file that owns the accumulator rather than
   promoted to its own module for a five-line sort).
2. `src/userStream.ts` — the `fills` branch: map the ordered copy; route status
   / `quantity` through `krakenOpenOrderFill`.
3. `test/krakenFillCumulative.test.ts` — already written (gate 2), red.

No `package.json`, no dependency, no new file in `src/`.

## 3. Blast Radius

1. **Other call sites.** `prepareKrakenOrderMsg` has exactly one caller
   (`src/userStream.ts:3382`, the Kraken `message` handler) and the `fills`
   branch is reached only for `ExchangeEnum.krakenUsdm` + `feed === 'fills'`.
   `_snapshot` feeds return earlier (`:3372`), so this branch never sees a
   snapshot. Binance / Bybit / OKX / KuCoin / Coinbase / Hyperliquid / Kraken
   **spot** all take different branches and are untouched.
2. **`core/` submodule — YES.** This is `websocket-connector-sh`, shared with
   prod `binance-websocket`, the self-hosted stack and every other consumer of
   the `*-sh` family. Danger List #11. The parent pointer must be bumped
   deliberately at ship time.
3. **Owned/emitted contract.** `ExecutionReport` field *shapes* are unchanged —
   same keys, same types. What changes is the *ordering and value* of
   `orderStatus` / `quantity` within one Kraken futures batch. `app-sh`'s
   `convertExecutionReportToOrder` → `onFilled` / `onPartiallyFilled` is the
   consumer; it already handles a PARTIALLY_FILLED-then-FILLED sequence — that
   is the normal single-fill-per-message path today. No Redis channel, no
   RabbitMQ queue, no socket.io event name is touched.
4. **Other tests on this path.** `test/krakenFillCumulative.test.ts`'s four
   pre-existing tests (a777b8d) all emit one fill per message and must stay
   green — they pin that the single-fill path is unchanged.
   `test/krakenSpotExecutionStatus.test.ts` and `krakenSpotBalances.test.ts`
   cover the sibling spot branches. Full suite: 73 green before this change.

## 5. Gate 4 — plan vs spec

Walked §1–§5. Every numbered section appears above. The one divergence is
§4.3, resolved *in this plan's §1.2* with its reasoning rather than silently
skipped; the spec's §4.2 is satisfied by a different mechanism than §4.2
literally proposed (existing helper instead of a new monotonic accumulator),
and §4.3 falls away as a consequence. The fix targets §3's named root cause
(no ordering) rather than the symptom (a wrong status value).
