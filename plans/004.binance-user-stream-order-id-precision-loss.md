# 004 — Plan: Binance user-stream order ids above 2^53

Spec: [`../specs/004.binance-user-stream-order-id-precision-loss.md`](../specs/004.binance-user-stream-order-id-precision-loss.md)

## 1. Solution

Spec §3 puts the defect inside the vendor SDK's `JSON.parse`, before our listener runs, so the fix
has to change **the parse**, not the mapper.

`binance@3.5.5` exposes a supported hook for exactly this:
`WSClientConfigurableOptions.customParseJSONFn?: (raw: string) => object`
(`binance/lib/types/websockets/ws-general.d.ts:100`), consumed by `parseRawWsMessage`
(`websocket-util.js:798-800`) — the same line spec §3 names as the truncation point. Supplying it
replaces the bare `JSON.parse` with ours and touches nothing else.

The parser quotes any `"i": <digits>` whose value exceeds 2^53, so `JSON.parse` yields the exact
digits as a string. Below 2^53 it does nothing at all (§4.3.1).

**Why not a vendored `WebsocketClient` subclass** (the shape the triage brief suggested, mirroring
`bybit-custom/websocket-client.ts`): `bybit-custom` exists because `bybit-api` has *no* parse hook,
so the only seam there is a fork — and that fork is 891 lines pinned to `bybit-api` exact `4.1.17`,
which the repo CLAUDE.md already calls out as a maintenance hazard. Here the parse is reached only
through `resolveEmittableEvents`, so a subclass would mean copying that whole ~60-line method to
change one argument, and re-copying it on every SDK bump. The hook is the same *seam* with none of
that. It is also what the sibling repo already did for the REST half of this same defect
(`exchange-connector-sh core/src/binance-custom/index.ts` injects axios `transformResponse` rather
than forking the client), so this keeps the two halves symmetrical.

## 2. Build order

1. `src/binance-custom/losslessOrderId.ts` — the raw-text rewrite + a `JSON.parse` wrapper.
2. `src/binance-custom/index.ts` — `withLosslessOrderIds(options)`, which adds
   `customParseJSONFn` unless the caller already chose one.
3. `src/userStream.ts` — wrap the options at the three Binance client constructions
   (`:1854` binanceUS, `:1867` Ed25519 WS-API spot, `:1899` spot/usdm/coinm).
4. Delete the gate-2 skeleton body; tests go green.

### 2.1 Contract decisions the spec left open

- **Key set = `{'i'}` only.** §4.1.2 fixes the field; this fixes the spelling. `i` is the order id
  in both frame shapes. The REST spelling `orderId` is deliberately **not** included: the only
  `orderId`-shaped payloads on these sockets would be WS-API *order* responses, and `userStream.ts`
  only ever calls `subscribeUserDataStream` — it places no orders. Adding it would be speculative.
  A kline's `i` (the interval, `"1m"`) is a JSON string and is skipped whole by §4.3.2's rule
  anyway, and klines do not travel on a user stream.
- **Rewrite in raw text, not a bigint JSON parser.** The digits only exist in the frame text, and
  `json-bigint` would return `BigInt` values that `JSON.stringify` throws on at
  `userStream.ts:3859`. No new dependency (§3.1).
- **Injected at the call sites, not by subclassing the client**, so the price/candle connectors
  (§4.2.2) and every other venue (§4.3.5) are untouched by construction.

### 2.2 Port, not reuse — and why

`exchange-connector-sh core/src/binance-custom/losslessOrderId.ts` already solves the raw-text
rewrite and is shipped and tested. It is in a **different repo's** core submodule; the two cores
share no package, so it cannot be imported. This is the same situation as `src/utils/redact.ts`,
which this repo already keeps as a deliberate copy of the exchange-connector one.

It is a port rather than a byte-identical copy for one reason: the shipped file hardcodes
`UNSAFE_INT_KEYS = new Set(['orderId'])`, the REST spelling. The WS wire spelling is `i`.
Parameterising the shipped file instead would mean editing a second repo's core, which is a
separate ship. The scanner logic (string-literal awareness, key detection, the safe-integer guard,
the non-JSON passthrough) is carried over unchanged, and the header points at the original.

### 2.3 JIT legacy tier

**Tier 2 (fully pure)** for the new module: `losslessOrderId.ts` takes a string and returns a
value, importing nothing. `withLosslessOrderIds` is a pure options transform.

`userStream.ts` is legacy spaghetti on this path (a 4,797-line class mixing transport, auth
backoff and Redis), but Tier 0 applies to it: the change is three call sites adding one wrapped
argument, which is not "already touching" the decision logic around them. Extracting Binance client
construction out of `openStreamCallback` would be a rewrite sprung on a bug fix.

## 3. Blast radius

1. **Other call sites of what changes.** `withLosslessOrderIds` is new — no existing callers.
   `grep -n "new WebsocketClient\|WebsocketAPIClient(" src/` returns exactly the three
   `userStream.ts` lines in step 3; `src/price/binance.ts` builds its own clients through
   `getBinanceClient()` and is not touched.
2. **This is `core/` — `websocket-connector-sh`.** Shared/public/deployed platform-wide, and the
   parent pointer must be bumped at ship. Deploy is the ws fleet: `userStream` +
   `userStreamWorker`, which live in *two different prod checkouts* (repo CLAUDE.md "Deploy
   topology"), so both need building.
3. **Contracts this repo owns.** The Redis market-data channels and the RabbitMQ
   `archiveCandleWrite` payload are untouched. The **account channel payload** changes:
   `orderId` becomes a string above 2^53. That is a Danger-List-adjacent shape change with exactly
   one consumer, main-app, checked field by field in spec §5 — the field is already
   `RequiredString` in mongo (§5.1), already `number | string` in the local type, and the two
   strict comparisons on it are Kraken-only (§5.3). `main-app-sh`'s `OrderUpdate.orderId: number`
   becomes documentation-stale (§5.5); it is a separate repo and does not break the build.
4. **Other tests on this path.** `test/userStreamAuthBackoff.test.ts` constructs `UserConnector`
   and exercises the same Binance branch's auth handling; it must stay green. The other four
   `test/*.test.ts` cover non-Binance venues and are unaffected. Full `npm test` is the gate.

## 5. Gate 4 — plan verified against spec

Walked §1-§5. Every numbered section appears in §4 above. The Solution changes the parse
(§3's named root cause), not `utils/binance.js:228` (which §3 explicitly clears). The only
decisions taken here — key set, rewrite-in-text, injection point — are ones the spec left open;
none contradicts it. §4.2.1 (no backfill) and §4.2.2/§4.2.3 (price connector, REST) are honoured by
scope. §5.5 records a known-stale type in another repo rather than silently widening it here.
